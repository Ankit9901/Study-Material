Dataflow — Deep Dive

🌊 Google Cloud Dataflow

A fully managed, serverless data processing service used for batch and streaming data pipelines, based on the Apache Beam programming model.

Definition (word-by-word)

  • Google Cloud — GCP (Google Cloud Platform), Google's suite of cloud computing services hosted in Google's global data centers.
  • Dataflow — The name of the service. "Data" = the information being processed. "Flow" = the movement/transformation of that data through a pipeline — like water flowing through pipes, being filtered and transformed along the way.
  • Fully managed — Google manages ALL infrastructure: servers, OS updates, patches, networking, monitoring, restarts. You only write code; Google runs the machines.
  • Serverless — There are no servers you provision or see. You don't pick VM sizes, start clusters, or shut them down. Resources are allocated invisibly and automatically on demand. You pay only for actual usage, not for idle machines.
  • Data processing service — A service whose core job is to read data, transform it (clean, aggregate, join, enrich), and write it somewhere else. It processes — it doesn't store or query interactively.
  • Batch — Processing a finite, bounded set of data that already exists. Example: process last month's sales records at midnight. Has a defined start and end.
  • Streaming — Processing an infinite, continuous, unbounded flow of data as it arrives in real time. Example: process every click event from a website the moment it happens.
  • Data pipelines — A sequence of steps (stages) that data passes through: Read → Transform → Write. Like an assembly line for data.
  • Apache Beam — An open-source unified programming model (SDK) for building both batch and streaming pipelines. "Beam" = Batch + strEAM. Write your pipeline once in Beam; run it on Dataflow (or Spark, Flink, etc.).
  • Programming model — The mental framework and API you use to write your data transformations. Beam's model: PCollections (parallel collections of data) + PTransforms (parallel transformations on that data).

Processing Type: Batch + Streaming (via Beam) P3

P3 refers to Dataflow's pricing/runner tier. Dataflow Prime (sometimes noted as the 3rd generation of Dataflow runner) brings vertical autoscaling and right-fitting of worker resources automatically.
  • Batch processing — You have a complete dataset (e.g., a CSV file, a database table). You run the pipeline once, process all records, and the job ends. Example: nightly ETL to load a data warehouse.
  • Streaming processing (via Beam) — Data flows in continuously (e.g., from Pub/Sub). The pipeline runs forever, processing each new record as it arrives. Example: live fraud detection, real-time dashboards.
  • "via Beam" — Both modes use the same Apache Beam API. The same code handles batch and stream — Beam abstracts the difference. Only the runner (Dataflow) knows whether the source is bounded or unbounded.

Serverless: Yes

  • No cluster to create. No VM to choose. No autoscaling rules to configure manually.
  • Dataflow automatically determines how many workers are needed, spins them up, scales during the job, and tears them down when done.
  • Billing is per-vCPU-second and per-GB-second of RAM used, not per hour of reserved instances.

Programming: Apache Beam (Python, Java, Go)

  • Python — Most popular for data engineers and data scientists. Easiest to prototype quickly.
  • Java — The original Beam language. Most mature SDK. Used in enterprise environments.
  • Go — Newer Beam SDK. High performance, used for high-throughput scenarios.
  • Key Beam concepts: Pipeline (the job), PCollection (distributed dataset), PTransform (operation: ParDo, GroupByKey, Combine, Flatten, Partition), Runner (execution engine — Dataflow is a runner).

Use Case Focus: ETL, Real-time Pipelines

  • ETL = Extract, Transform, Load. The classic data engineering pattern:
    • Extract — Pull data from a source (database, API, file storage, Pub/Sub).
    • Transform — Clean it (remove nulls), enrich it (add columns), aggregate it (sum by region), join it (merge two datasets).
    • Load — Write to a destination (BigQuery, Cloud Storage, Bigtable, database).
  • Real-time pipelines — Continuous pipelines that process data within milliseconds to seconds of arrival. Used for live analytics, alerting systems, event-driven architectures.

Management: Fully Managed, Auto-Scaled

  • Fully managed — Zero infrastructure ops. No SSH into workers. No monitoring of cluster health. No OS patches.
  • Auto-scaled — Dataflow's autoscaler watches your pipeline's throughput and backlog. If data is piling up, it adds workers. If the pipeline is idle or finishing, it removes workers. This is Horizontal Autoscaling (adding/removing VMs) and can also right-fit worker shapes (Dataflow Prime).

Dataproc — Deep Dive

🔥 Google Cloud Dataproc

A fully managed and fast cloud service by Google Cloud for running Apache Spark, Apache Hadoop, and other open-source big data tools.

Definition (word-by-word)

  • Google Cloud Dataproc — "Data" + "proc" (processing). GCP's managed service for running open-source distributed computing frameworks.
  • Fully managed — Google provisions clusters, installs Spark/Hadoop, manages OS, networking, and security. Cluster operations (create/delete/resize) take 90 seconds vs. hours for self-managed.
  • Fast — Clusters spin up in ~90 seconds (traditional Hadoop clusters take 10–20 minutes). Also, it uses Google's high-speed internal network.
  • Cloud service — Runs entirely on GCP infrastructure. Data is typically in Cloud Storage (GCS), not HDFS (Hadoop's local disk storage).
  • Apache Spark — An open-source, in-memory distributed computing engine. "In-memory" = data is processed in RAM, not read/written to disk at every step → much faster than MapReduce. Used for large-scale data processing, ML (MLlib), SQL (Spark SQL), and streaming (Structured Streaming).
  • Apache Hadoop — The original big data framework. Consists of: HDFS (distributed file system), YARN (resource manager), MapReduce (batch computation). Older than Spark, disk-based, but still widely used.
  • Open-source big data tools — Dataproc also supports: Hive (SQL over Hadoop), Pig (scripting language for MapReduce), Presto (fast SQL), Jupyter (notebooks), Zeppelin (interactive notebooks), Flink (stream processing).

Processing Type: Mostly Batch (Spark Streaming exists)

  • Mostly batch — The primary and most common use case is batch: process a large static dataset (files in GCS, tables in BigQuery). Jobs have a defined end.
  • Spark Streaming exists — Spark includes a streaming module (Structured Streaming) that can process live data from Kafka or Pub/Sub. However, this is not Dataproc's primary strength. Dataflow is preferred for real-time streaming on GCP.

Serverless: No (Cluster-based)

  • Cluster-based — You explicitly create a Dataproc cluster specifying: machine type (n1-standard-4, etc.), number of worker nodes, disk size, preemptible (spot) VMs, optional components (Jupyter, Presto, etc.).
  • The cluster persists until you delete it. You are billed for every second the cluster exists, even if no jobs are running.
  • Dataproc Serverless — A newer option that removes cluster management for Spark batch jobs. But the classic Dataproc is cluster-based as described in the notes.

Programming: Spark, Hadoop (Java, Python, Scala)

  • Java — Original language for both Hadoop MapReduce and Spark. Verbose but fast and type-safe.
  • Python — PySpark (Python API for Spark). Most popular today among data engineers. Easy to prototype.
  • Scala — Spark is written in Scala. The most performant way to write Spark jobs. Functional programming style. Compiles to JVM bytecode.

Use Case Focus: Legacy Migration, ML, Analytics

  • Legacy migration — Organizations running on-premises Hadoop clusters can "lift and shift" to Dataproc with minimal code changes. Same Spark/Hadoop APIs, but on GCP. Migrate without rewriting your entire codebase.
  • ML (Machine Learning) — Spark MLlib provides distributed ML algorithms (classification, regression, clustering, collaborative filtering). Train models on datasets too large for a single machine.
  • Analytics — Run large-scale analytical queries using Hive or Spark SQL over petabytes of data stored in Cloud Storage.

Management: You Manage Cluster Size/Configs

  • YOU choose: how many master nodes (usually 1 or 3 for HA), how many worker nodes, VM sizes, disk types, network settings, IAM permissions, initialization scripts.
  • YOU decide when to scale: manually resize the cluster, or configure Autoscaling Policies (but you define the min/max bounds).
  • YOU are responsible for: not leaving idle clusters running (wasting money), choosing the right machine type for your workload, managing Hadoop configurations (yarn-site.xml, spark-defaults.conf).

Cloud Composer — Deep Dive

🎼 Google Cloud Composer

A fully managed workflow orchestration service built on Apache Airflow.

Definition (word-by-word)

  • Google Cloud Composer — "Composer" = someone who orchestrates a musical composition. Here it orchestrates data workflows — telling each instrument (service/task) when to play.
  • Fully managed — GCP installs Airflow, manages the web server, the scheduler, the metadata database, the worker pool, and all updates.
  • Workflow orchestration service —
    • Workflow — A sequence of dependent tasks. Task B runs after Task A succeeds. Task C and D can run in parallel after B.
    • Orchestration — Coordinating when and how each step runs. Setting dependencies, handling retries, sending alerts on failure.
    • Service — Delivered as a GCP product. No need to self-host Airflow.
  • Apache Airflow — An open-source platform (originally created by Airbnb in 2014) to programmatically author, schedule, and monitor workflows. Workflows are written as Python DAGs.

What is a DAG?

DAG = Directed Acyclic Graph. Directed = tasks have direction (A → B, not B → A). Acyclic = no cycles (no task can depend on itself, directly or indirectly). Graph = a set of nodes (tasks) connected by edges (dependencies). Each node is a task; each edge says "run me after this other task succeeds."

Processing Type: Workflow Scheduling / Orchestration

  • Composer does NOT process data itself. It coordinates other services that process data.
  • Example DAG: (1) Trigger a Dataflow job → (2) When it finishes, run a BigQuery query → (3) Export results to Cloud Storage → (4) Send a Slack notification.
  • Composer manages this entire sequence: scheduling, retries, dependencies, alerting.

Management: Fully Managed by GCP

  • Airflow installation — GCP installs the correct version of Airflow for you. No pip install, no environment setup.
  • Upgrades — GCP upgrades Airflow versions with minimal downtime. No manual migration work.
  • Scaling — Composer automatically scales the number of Airflow workers up or down based on how many DAG runs are queued.
  • Monitoring — Integrated with Cloud Monitoring and Cloud Logging. Airflow logs are streamed to Cloud Logging automatically. You get dashboards for DAG run health out of the box.

Use Case Focus: Pipeline Orchestration, Scheduling

  • Schedule nightly ETL jobs (e.g., "run this Dataflow job every day at 2 AM").
  • Manage complex multi-step ML pipelines: data prep → training → evaluation → deployment.
  • Cross-service coordination: BigQuery → Dataproc → Cloud Storage → Email notification, all in one DAG.
  • Dependency management: "Don't run step 3 until step 1 AND step 2 both succeed."
  • Retry policies: "If the task fails, retry 3 times with exponential backoff."

Pub/Sub — Deep Dive

📡 Google Cloud Pub/Sub

A real-time messaging service that lets applications communicate asynchronously by sending and receiving messages via topics and subscriptions.

Definition (word-by-word)

  • Google Cloud Pub/Sub — "Pub" = Publish. "Sub" = Subscribe. The Publish-Subscribe messaging pattern. A globally scalable, fully managed message bus.
  • Real-time messaging service — Messages are delivered within milliseconds of being published. "Real-time" = extremely low latency, not batch. "Messaging" = data is packaged as discrete messages (not streams of bytes).
  • Applications communicate asynchronously —
    • Asynchronously — The sender (publisher) does NOT wait for the receiver (subscriber) to process the message. It fires and forgets. The receiver processes it whenever it is ready. This decouples producer and consumer.
    • Synchronous (the opposite) — The caller waits for a response before continuing. Example: a REST API call. If the server is slow, the caller is blocked.
  • Sending and receiving messages — Publishers send messages. Subscribers receive them. These are independent operations — publisher doesn't know who will receive the message.
  • Topics — A named channel or feed to which publishers send messages. Example: "user-clicks", "order-placed", "sensor-readings". A publisher sends to a topic, not to a specific subscriber.
  • Subscriptions — A named resource that represents a subscriber's interest in a topic. Multiple subscriptions can exist on one topic — each subscription receives ALL messages independently (fan-out).

Use Case Focus: Publishers Send Messages to a Topic

Flow: Publisher → Topic → Subscription → Subscriber

Publisher: "I have a new order" → publishes to topic "orders".
Subscription A (Inventory Service) receives it → updates stock.
Subscription B (Email Service) receives it → sends confirmation email.
Subscription C (Analytics) receives it → logs to BigQuery.
  • Decoupling — The order service doesn't know or care about inventory/email/analytics. It just publishes. New consumers can be added without changing the publisher.
  • Fan-out — One message published to a topic is delivered to ALL subscriptions on that topic independently.
  • Buffering — If a subscriber is temporarily down, messages are retained (up to 7 days by default). No messages are lost.
  • Load balancing — Multiple instances of the same subscriber share a subscription → messages are distributed across them (not duplicated). This allows horizontal scaling of consumers.

Management: Subscribers Pull or Receive Messages via a Subscription

  • Pull delivery — The subscriber actively requests messages from Pub/Sub. "Hey, do you have anything for me?" Used when the subscriber controls the consumption rate.
  • Push delivery — Pub/Sub actively sends messages to a subscriber's HTTP/HTTPS endpoint (webhook). "Hey subscriber, here's a new message." Used for event-driven serverless functions (Cloud Run, Cloud Functions).
  • Acknowledgement (ack) — After processing a message, the subscriber sends an "ack" to Pub/Sub to confirm delivery. If the ack deadline expires without an ack, Pub/Sub re-delivers the message (at-least-once delivery).

Serverless: Yes

  • No infrastructure to manage. No brokers to run, no Kafka clusters to maintain.
  • Fully serverless and globally distributed. Scales to millions of messages per second automatically.
  • GCP handles durability, replication, and delivery guarantees.

Common Pub/Sub Use Cases

  • Ingesting IoT sensor data into BigQuery or Dataflow.
  • Event-driven microservices communication.
  • Streaming logs from applications to storage.
  • Triggering Cloud Functions on events (file uploaded, record created).
  • Decoupling frontend click events from backend analytics processing.

Complete Glossary — Every Key Term

Apache Beam

Unified open-source SDK to build both batch and streaming pipelines. "Beam" = Batch + strEAM. Run on Dataflow, Spark, Flink.

Apache Spark

In-memory distributed data processing engine. Much faster than Hadoop MapReduce. Supports SQL, ML, streaming, graph processing.

Apache Hadoop

Original big data framework. Includes HDFS (storage) + MapReduce (compute) + YARN (resource management). Disk-based, batch-only.

Apache Airflow

Open-source workflow orchestration platform. Write DAGs in Python to schedule and monitor tasks across any system.

ETL

Extract → Transform → Load. The standard pattern for moving data between systems while cleaning and reshaping it.

Batch Processing

Process a finite, bounded dataset in one job run. Has a clear start and end. Example: daily report generation.

Stream Processing

Process an infinite, continuous flow of data as it arrives. No end. Example: live fraud detection on card transactions.

Serverless

No infrastructure to provision or manage. Cloud auto-scales and bills per usage. You only write and deploy code.

Cluster-based

You provision a group of VMs (a cluster). You choose count and size. You manage its lifecycle. Example: Dataproc clusters.

Fully Managed

The cloud provider handles all operational tasks: installation, upgrades, monitoring, scaling, patching. You focus on logic.

Auto-scaled

The system automatically adds or removes compute resources based on current load, without manual intervention.

DAG

Directed Acyclic Graph. Nodes = tasks, edges = dependencies. No cycles allowed. Used in Airflow/Composer to define workflow order.

Topic (Pub/Sub)

A named channel in Pub/Sub to which publishers send messages. Subscribers don't connect to publishers — they connect to topics.

Subscription (Pub/Sub)

A named resource that represents interest in a topic. Each subscription receives all messages independently (fan-out).

Publisher

An application or service that creates and sends messages to a Pub/Sub topic. Does not know who the subscribers are.

Subscriber

An application or service that receives messages from a Pub/Sub subscription. Pulls or is pushed messages.

Asynchronous

The sender does not wait for the receiver to process the message. Fire and forget. Enables loose coupling between services.

Legacy Migration

Moving existing on-premises workloads (old Hadoop clusters) to the cloud with minimal code changes. Dataproc's strength.

PCollection

Beam's distributed dataset. Can be bounded (batch) or unbounded (stream). Every Beam transformation takes PCollections as input/output.

PTransform

A data processing step in Apache Beam. ParDo (map), GroupByKey (shuffle), Combine (reduce), Flatten (merge), Partition (split).

Orchestration

Coordinating the execution order of multiple tasks/services. Defining: what runs when, in what order, what to do on failure.

GCP

Google Cloud Platform. Google's cloud computing product suite: compute, storage, databases, networking, ML, analytics, and more.

When to Use Which Service

Use Dataflow when...

  • You need real-time streaming and batch in one unified pipeline.
  • You want fully serverless — zero cluster management.
  • Your team writes in Python, Java, or Go using Apache Beam.
  • You are building new ETL pipelines on GCP from scratch.

Use Dataproc when...

  • You have existing Spark or Hadoop jobs to migrate to the cloud.
  • You need to run ML training jobs with Spark MLlib.
  • You want to use Hive, Pig, Presto, or other Hadoop ecosystem tools.
  • You are comfortable managing cluster sizing yourself for cost optimization.

Use Cloud Composer when...

  • You need to schedule and sequence multiple jobs across different GCP services.
  • Your pipelines have complex dependencies (task A before B and C, then D).
  • You want retry logic, alerting, and a visual DAG monitoring UI.
  • You already use Apache Airflow on-premises and want a managed version.

Use Pub/Sub when...

  • You need to decouple services — producer should not know about consumers.
  • You need to fan-out one event to multiple downstream systems.
  • You are ingesting high-volume real-time events (IoT, clickstreams, logs).
  • You need a buffer between a fast producer and a slow consumer.
