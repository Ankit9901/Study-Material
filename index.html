When to Use Which

Use Dataflow when…

  • You need real-time streaming and batch in one unified pipeline
  • You want fully serverless — zero cluster management
  • Your team writes Python, Java, or Go using Apache Beam
  • You are building new ETL pipelines on GCP from scratch

Use Dataproc when…

  • You have existing Spark or Hadoop jobs to migrate to the cloud
  • You need ML training with Spark MLlib
  • You want Hive, Pig, Presto or other Hadoop ecosystem tools
  • You are comfortable managing cluster sizing yourself

Use Composer when…

  • You need to schedule and sequence multiple jobs across GCP services
  • Your pipelines have complex dependencies (task A before B and C, then D)
  • You want retry logic, alerting, and a visual DAG monitoring UI
  • You already use Apache Airflow on-premises

Use Pub/Sub when…

  • You need to decouple services — producer should not know about consumers
  • You need to fan-out one event to multiple downstream systems
  • You are ingesting high-volume real-time events (IoT, clickstreams, logs)
  • You need a buffer between a fast producer and a slow consumer

🌊 Google Cloud Dataflow

A fully managed, serverless data processing service for batch and streaming pipelines, based on the Apache Beam programming model.

Definition — word by word

  • Google Cloud — GCP (Google Cloud Platform), Google's suite of cloud computing services hosted in Google's global data centers.
  • Dataflow — "Data" = the information processed. "Flow" = movement/transformation through a pipeline — like water through pipes, filtered and transformed along the way.
  • Fully managed — Google manages ALL infrastructure: servers, OS updates, patches, networking, monitoring, restarts. You only write code.
  • Serverless — No servers to provision or see. No VM sizes, no clusters to start or shut down. Resources allocated invisibly on demand. Pay only for actual usage.
  • Data processing service — Reads data, transforms it (clean, aggregate, join, enrich), and writes it somewhere else. Processes — doesn't store or query interactively.
  • Batch — Processing a finite, bounded dataset that already exists. Example: process last month's sales records at midnight. Has a defined start and end.
  • Streaming — Processing an infinite, continuous, unbounded flow of data as it arrives in real time. Example: process every click event the moment it happens.
  • Data pipelines — A sequence of steps that data passes through: Read → Transform → Write. Like an assembly line for data.
  • Apache Beam — Open-source unified programming model for both batch and streaming pipelines. "Beam" = Batch + strEAM. Write once; run on Dataflow, Spark, or Flink.
  • Programming model — The mental framework and API for writing transformations. Beam's model: PCollections (parallel datasets) + PTransforms (parallel operations on them).

Processing Type: Batch + Streaming (via Beam) P3

P3 = Dataflow Prime — the 3rd-generation runner. Brings vertical autoscaling and automatic right-fitting of worker resources. Chooses the optimal machine shape for each stage of your pipeline.
  • Batch — Complete dataset (CSV, database table). Run once, process all, job ends. Example: nightly ETL to load a data warehouse.
  • Streaming (via Beam) — Data flows in continuously (e.g., from Pub/Sub). Pipeline runs forever. Example: live fraud detection, real-time dashboards.
  • "via Beam" — Both modes use the same Beam API. Same code handles batch and stream — Beam abstracts the difference. Only the runner (Dataflow) knows if the source is bounded or unbounded.

Serverless: Yes

  • No cluster to create. No VM to choose. No autoscaling rules to configure manually.
  • Dataflow determines how many workers are needed, spins them up, scales during the job, tears them down when done.
  • Billing: per-vCPU-second and per-GB-second of RAM used — not per hour of reserved instances.

Programming: Apache Beam (Python, Java, Go)

  • Python — Most popular for data engineers and scientists. Easiest to prototype quickly.
  • Java — Original Beam language. Most mature SDK. Used in enterprise environments.
  • Go — Newer Beam SDK. High performance for high-throughput scenarios.
  • Key Beam concepts: Pipeline (the job), PCollection (distributed dataset), PTransform (ParDo, GroupByKey, Combine, Flatten, Partition), Runner (execution engine — Dataflow is a runner).

Use Case: ETL, Real-time Pipelines

  • ETL = Extract, Transform, Load:
    • Extract — Pull data from a source (database, API, GCS, Pub/Sub).
    • Transform — Clean (remove nulls), enrich (add columns), aggregate (sum by region), join (merge datasets).
    • Load — Write to destination (BigQuery, Cloud Storage, Bigtable).
  • Real-time pipelines — Continuous pipelines processing data within milliseconds of arrival. Used for live analytics, alerting, event-driven architectures.

Management: Fully Managed, Auto-Scaled

  • Fully managed — Zero infrastructure ops. No SSH into workers, no cluster health monitoring, no OS patches.
  • Auto-scaled — Dataflow's autoscaler watches throughput and backlog. If data piles up → adds workers. If idle or finishing → removes workers. Horizontal Autoscaling (adding/removing VMs).

Classic GCP Streaming Architecture

Pub/Sub (ingest events) → Dataflow (transform + window + aggregate) → BigQuery (store + query)

Dataflow windowing types:
 • Fixed window — every 5 min
 • Sliding window — last 10 min, updated every 1 min
 • Session window — group by user inactivity gap

Watermarks: Dataflow tracks how far behind real-time data is.
When watermark passes window end → emit results (even if some late data may arrive).

🔥 Google Cloud Dataproc

A fully managed and fast cloud service for running Apache Spark, Apache Hadoop, and other open-source big data tools.

Definition — word by word

  • Dataproc — "Data" + "proc" (processing). GCP's managed service for open-source distributed computing frameworks.
  • Fully managed — Google provisions clusters, installs Spark/Hadoop, manages OS/networking/security. Cluster operations take ~90 seconds vs hours for self-managed.
  • Fast — Clusters spin up in ~90 seconds (traditional Hadoop clusters take 10–20 minutes). Uses Google's high-speed internal network.
  • Cloud service — Runs entirely on GCP. Data is typically in Cloud Storage (GCS), not HDFS.
  • Apache Spark — Open-source, in-memory distributed computing engine. "In-memory" = data processed in RAM, not read/written to disk at every step → much faster than MapReduce. Supports ML (MLlib), SQL (Spark SQL), streaming (Structured Streaming).
  • Apache Hadoop — The original big data framework: HDFS (distributed file system) + YARN (resource manager) + MapReduce (batch computation). Older than Spark, disk-based, still widely used.
  • Open-source big data tools — Dataproc also supports: Hive (SQL over Hadoop), Pig (scripting for MapReduce), Presto (fast SQL), Jupyter, Zeppelin, Flink.

Processing Type: Mostly Batch (Spark Streaming exists)

  • Mostly batch — Primary use case: process a large static dataset (files in GCS). Jobs have a defined end.
  • Spark Streaming exists — Spark's Structured Streaming can process live data from Kafka or Pub/Sub. But Dataflow is preferred for real-time streaming on GCP.

Serverless: No (Cluster-based)

  • Cluster-based — You explicitly create a cluster specifying: machine type, number of workers, disk size, preemptible (spot) VMs, optional components (Jupyter, Presto, etc.).
  • The cluster persists until you delete it. Billed every second the cluster exists, even when idle.
  • Cost tip — Use preemptible (spot) VMs for workers (up to 80% cheaper). Delete the cluster when the job finishes. Only use standard VMs for the master node.
  • Dataproc Serverless — Newer option that removes cluster management for Spark batch jobs. Classic Dataproc is still cluster-based.

Programming: Spark, Hadoop (Java, Python, Scala)

  • Java — Original language for Hadoop MapReduce and Spark. Verbose but fast and type-safe.
  • Python — PySpark (Python API for Spark). Most popular today. Easy to prototype.
  • Scala — Spark is written in Scala. Most performant. Functional programming style. Compiles to JVM bytecode.

Use Case: Legacy Migration, ML, Analytics

  • Legacy migration — Organisations running on-premises Hadoop clusters can "lift and shift" to Dataproc with minimal code changes. Same Spark/Hadoop APIs, but on GCP.
  • ML — Spark MLlib provides distributed ML algorithms (classification, regression, clustering, collaborative filtering). Train models on datasets too large for a single machine.
  • Analytics — Run large-scale analytical queries using Hive or Spark SQL over petabytes of data stored in GCS.

Management: You Manage Cluster Size/Configs

  • YOU choose: how many master nodes (1 or 3 for HA), worker node count, VM sizes, disk types, network settings, IAM permissions, initialization scripts.
  • YOU decide when to scale: manually resize, or configure Autoscaling Policies (you define min/max bounds).
  • YOU are responsible for: not leaving idle clusters running, choosing the right machine type, managing Hadoop configurations (yarn-site.xml, spark-defaults.conf).

🎼 Google Cloud Composer

A fully managed workflow orchestration service built on Apache Airflow.

Definition — word by word

  • Composer — "Composer" = someone who orchestrates a musical composition. Here it orchestrates data workflows — telling each instrument (service/task) when to play.
  • Fully managed — GCP installs Airflow, manages the web server, the scheduler, the metadata database, the worker pool, and all updates.
  • Workflow — A sequence of dependent tasks. Task B runs after Task A succeeds. Task C and D can run in parallel after B.
  • Orchestration — Coordinating when and how each step runs. Setting dependencies, handling retries, sending alerts on failure.
  • Apache Airflow — Open-source platform (created by Airbnb in 2014) to programmatically author, schedule, and monitor workflows. Workflows are written as Python DAGs.

What is a DAG?

DAG = Directed Acyclic Graph.
Directed = tasks have direction (A → B, not B → A).
Acyclic = no cycles (no task can depend on itself, directly or indirectly).
Graph = nodes (tasks) connected by edges (dependencies). Each edge says "run me after this other task succeeds."

Airflow Operators (task types)

  • BashOperator — Run a shell command.
  • PythonOperator — Run a Python function.
  • BigQueryOperator — Execute a SQL query in BigQuery.
  • DataflowCreateJavaJobOperator — Start a Dataflow job.
  • SlackAPIPostOperator — Send a Slack message.
  • Hundreds more operators for GCP, AWS, databases, HTTP, email, etc.

Management: Fully Managed by GCP

  • Airflow installation — GCP installs the correct version of Airflow for you. No pip install, no environment setup.
  • Upgrades — GCP upgrades Airflow versions with minimal downtime. No manual migration work.
  • Scaling — Composer automatically scales Airflow workers up or down based on how many DAG runs are queued.
  • Monitoring — Integrated with Cloud Monitoring and Cloud Logging. Airflow logs stream to Cloud Logging automatically. DAG run health dashboards out of the box.

Use Cases

  • Schedule nightly ETL jobs ("run this Dataflow job every day at 2 AM").
  • Manage complex multi-step ML pipelines: data prep → training → evaluation → deployment.
  • Cross-service coordination: BigQuery → Dataproc → Cloud Storage → Email notification — all in one DAG.
  • Dependency management: "Don't run step 3 until step 1 AND step 2 both succeed."
  • Retry policies: "If the task fails, retry 3 times with exponential backoff."

Example DAG flow

(1) Check if new file exists in GCS
(2) If yes → trigger Dataflow job
(3) Wait for completion
(4) Run BigQuery SQL transformation
(5) Export result to GCS
(6) Send Slack notification
(7) If ANY step fails → retry up to 3 times → alert PagerDuty

📡 Google Cloud Pub/Sub

A real-time messaging service that lets applications communicate asynchronously by sending and receiving messages via topics and subscriptions.

Definition — word by word

  • Pub/Sub — "Pub" = Publish. "Sub" = Subscribe. The Publish-Subscribe pattern. A globally scalable, fully managed message bus.
  • Real-time messaging — Messages delivered within milliseconds. "Real-time" = extremely low latency, not batch. "Messaging" = data packaged as discrete messages.
  • Asynchronously — The sender (publisher) does NOT wait for the receiver (subscriber) to process the message. Fire and forget. Receiver processes it whenever ready. Decouples producer and consumer.
  • Synchronous (the opposite) — The caller waits for a response before continuing. Example: a REST API call. If the server is slow, the caller is blocked.
  • Topics — A named channel to which publishers send messages. Example: "user-clicks", "order-placed", "sensor-readings". Publisher sends to a topic, not to a specific subscriber.
  • Subscriptions — A named resource representing a subscriber's interest in a topic. Multiple subscriptions can exist on one topic — each receives ALL messages independently (fan-out).

Flow

Publisher → Topic → Subscription → Subscriber

Publisher: "I have a new order" → publishes to topic "orders"
Subscription A (Inventory Service) → updates stock
Subscription B (Email Service) → sends confirmation email
Subscription C (Analytics) → logs to BigQuery

Key Concepts

  • Fan-out — One message published to a topic is delivered to ALL subscriptions independently. Each subscription gets its own copy.
  • Buffering — If a subscriber is temporarily down, messages are retained (up to 7 days by default). No messages are lost.
  • Load balancing — Multiple instances of the same subscriber share a subscription → messages distributed across them (not duplicated). Allows horizontal scaling of consumers.
  • Pull delivery — The subscriber actively requests messages. "Hey, do you have anything for me?" Used when subscriber controls the consumption rate.
  • Push delivery — Pub/Sub actively sends messages to a subscriber's HTTP/HTTPS endpoint (webhook). Used for event-driven serverless functions (Cloud Run, Cloud Functions).
  • Acknowledgement (ack) — After processing a message, subscriber sends an ack. If the ack deadline expires without ack, Pub/Sub re-delivers the message (at-least-once delivery).

Management

  • Fully serverless. No brokers to run, no Kafka clusters to maintain.
  • Globally distributed. Scales to millions of messages per second automatically.
  • GCP handles durability, replication, and delivery guarantees.

Common Use Cases

  • Ingesting IoT sensor data into BigQuery or Dataflow.
  • Event-driven microservices communication.
  • Streaming logs from applications to storage.
  • Triggering Cloud Functions on events (file uploaded, record created).
  • Decoupling frontend click events from backend analytics processing.

Cloud Pub/Sub — Real-time Messaging

  • Real-time messaging — Pub/Sub acts as the entry point for high-velocity event streams. IoT devices, mobile apps, web servers all publish events here continuously.
  • Decouples producers and consumers — The source system (producer) doesn't know who will consume the data. It just publishes to a topic. Downstream services (Dataflow, BigQuery, Cloud Functions) subscribe independently.
  • Why it's an ingestion tool — Buffers and delivers raw data reliably at any scale (millions of messages/second). The "front door" to your data platform.

Cloud Storage (GCS)

  • GCS = Google Cloud Storage. Globally distributed object storage. "Object" = any file (CSV, JSON, Parquet, Avro, images, logs). Access via URL, not file path.
  • Raw files — CSV = Comma-Separated Values (spreadsheet-like). JSON = JavaScript Object Notation (nested key-value pairs). Parquet = columnar binary format optimised for analytics (much smaller and faster than CSV for queries).
  • For processing — GCS is the staging area. Dataflow, Dataproc, BigQuery all read from GCS. It is the data lake landing zone.
  • 11 nines (99.999999999%) durability. Data replicated across multiple data centers automatically.

BigQuery Data Transfer Service (DTS)

  • BigQuery = GCP's serverless data warehouse.
  • Data Transfer Service — A managed connector that automatically schedules and runs data loads from external sources into BigQuery tables.
  • External SaaS — Software-as-a-Service products outside GCP: Google Ads (advertising data), Google Analytics (web traffic), S3 (Amazon Simple Storage Service — AWS's file storage). No code needed; configure a transfer job in the console.
  • Why it matters — Without DTS, you'd write custom scripts to call each SaaS API, handle pagination, auth tokens, retries, and schema mapping. DTS does all of this on a schedule automatically.

Storage Transfer Service

  • On-prem = On-premises. Your own data centres or office servers (not cloud). Data living here needs to be migrated to GCP.
  • AWS = Amazon Web Services. If you're migrating from AWS to GCP, Storage Transfer Service moves your S3 data to GCS automatically.
  • Difference from DTS — DTS is for SaaS data into BigQuery. Storage Transfer is for bulk file/object migration into GCS from other clouds or on-prem file servers.

Cloud Functions — Event-triggered Ingestion

  • Cloud Functions — Serverless Functions-as-a-Service (FaaS). Write a small function; GCP runs it in response to an event. No server to manage. Pay per invocation (100ms billing granularity).
  • Event-triggered — Runs only when a specific event fires: new file uploaded to GCS, new Pub/Sub message, an HTTP request, a Firestore document change.
  • Ingestion example — New file in GCS → function fires → reads file → validates it → transforms it → loads it into BigQuery or Pub/Sub. Zero manual intervention.

Dataflow — Serverless Stream + Batch

Use when you need unified batch + streaming with zero infrastructure management. Best for new GCP-native pipelines. Reads from Pub/Sub or GCS → PTransforms → writes to BigQuery or GCS. Auto-scaling handles spikes — adds/removes workers automatically.

Dataproc — Managed Spark/Hadoop

Use when you have existing Spark or Hadoop jobs to migrate. Your PySpark script reads from GCS, processes in distributed memory across all workers, writes output back to GCS or BigQuery. 10–100× faster than Hadoop MapReduce for typical jobs.

BigQuery — SQL Analytics + ELT

Use when transformation logic is expressible in SQL and data is already in BigQuery. ELT pattern — transform inside the warehouse. No separate processing cluster. Tools like dbt (data build tool) layer version control and testing on top.

ETL vs ELT — Key Difference

  • ETL (Dataflow approach) — Extract, Transform, Load. Transform data BEFORE loading into the warehouse. Transform happens in the pipeline. Good when transformation is complex and done in code.
  • ELT (BigQuery approach) — Extract, Load, Transform. Load raw data first, THEN transform inside BigQuery using SQL. Good when storage is cheap and SQL is powerful enough for transformations.

Cloud Composer — Orchestrate ETL workflows

Composer doesn't process data itself — it sequences other services. Example: schedule Dataflow job → wait → run BigQuery SQL transformation → export result to GCS.

Cloud Functions — Lightweight Transformation Scripts

  • Lightweight — Small, quick operations (not heavy multi-hour batch jobs). Example: parse 10 JSON records, format a date field, write to Firestore.
  • Event-driven — Runs in response to triggers (Pub/Sub message, GCS file, HTTP call). Perfect for microservices-style data pipelines.

🌊 Stream Processing

Processing data continuously as it arrives — real time, no waiting for a batch to accumulate

GCP ServiceDescription / Use Case
Cloud Pub/SubIngest and deliver streaming data
DataflowTransform and process streaming data from Pub/Sub
BigQuery StreamingInsert data into BigQuery in real-time
DatastreamReal-time Change Data Capture (CDC) from DBs to BigQuery

Cloud Pub/Sub — Universal Intake Valve

  • All real-time events (IoT sensors, app events, log lines) land in Pub/Sub first.
  • Delivers each message to all subscribers within milliseconds.
  • Durable — messages stored up to 7 days if a subscriber is slow.
  • Acts as the buffer between fast producers and potentially slower downstream processors.

Dataflow — Transform Streaming Data from Pub/Sub

  • Classic GCP streaming: Pub/Sub → Dataflow → BigQuery
  • Dataflow reads from a Pub/Sub subscription, applies transformations (filter, aggregate with windowing, enrich via lookups), writes results to BigQuery or GCS.
  • Windowing — In streaming, you can't wait for "all" data (it's infinite). Windows break the stream into finite chunks:
    • Fixed window (every 5 min)
    • Sliding window (last 10 min, updated every 1 min)
    • Session window (group by user inactivity gap)
  • Watermarks — Dataflow tracks how far behind real time the data is. The watermark tells Dataflow when it's safe to close a window and emit results, even if some late data may still arrive.

BigQuery Streaming — Insert Data in Real-time

  • BigQuery Streaming API — Insert individual rows into BigQuery tables immediately (not waiting for a batch load job). Rows are queryable within seconds of insertion.
  • Use case — Real-time dashboards that query BigQuery. If you insert every transaction as it happens, your dashboard shows up-to-the-minute data.
  • Cost note — Streaming inserts are more expensive per byte than batch loads. Use when you truly need real-time queryability.
  • BigQuery Storage Write API — The newer, more efficient replacement. Better cost, exactly-once semantics, and higher throughput.

Datastream — Change Data Capture (CDC)

  • Datastream — Serverless CDC and replication service. Continuously reads changes from operational databases and replicates them to BigQuery or GCS.
  • CDC = Change Data Capture. Instead of re-reading the entire database (expensive), CDC watches the database's transaction log (binary log in MySQL, WAL in PostgreSQL) and captures only changed rows: INSERTs, UPDATEs, DELETEs.
  • DBs → BigQuery — Source databases: MySQL, PostgreSQL, Oracle, SQL Server, AlloyDB. Destination: BigQuery (analytics) or GCS (archival or further Dataflow processing).
  • Why CDC? — Keeps your data warehouse always in sync with your operational database, in near-real-time, without hammering the source DB with full scans.

Cloud Storage — Data Lake Layer

  • Data lake — Stores vast amounts of raw data in native format until needed. Unlike a data warehouse (structured, schema-on-write), a data lake stores anything (structured, semi-structured, unstructured) without imposing a schema upfront.
  • Raw/staged data — Raw = exactly as received from source. Staged = partially cleaned but not yet loaded into final destination.
  • Unlimited storage, 11 nines (99.999999999%) durability. ~$0.02/GB/month for standard tier.

BigQuery — Enterprise Data Warehouse

  • Data warehouse — Stores and queries large volumes of historical, structured data for analytics and BI. Schema-on-write (define structure before loading). Optimised for complex analytical queries, not transactional updates.
  • Serverless — No clusters. Query petabytes; BigQuery auto-distributes across its internal infrastructure.
  • Columnar storage — Data stored column-by-column (not row-by-row). Analytics queries that read a few columns from millions of rows are vastly faster and cheaper.
  • BI tools (Looker, Data Studio, Tableau) connect directly to BigQuery for dashboards.

Cloud SQL — Managed Relational DB

  • Relational DB — Tables with rows and columns. ACID transactions. SQL query language.
  • Managed — GCP handles: installation, OS updates, automated backups, failover replicas, read replicas.
  • MySQL — World's most popular open-source RDBMS. Used by web apps.
  • PostgreSQL — Feature-rich open-source RDBMS. Supports JSON, arrays, full-text search, extensions.
  • SQL Server — Microsoft's commercial RDBMS. Used in enterprise Windows environments.
  • When to use — Operational/transactional workloads: web app backends, e-commerce order systems, CRM. NOT for analytical queries over billions of rows.

Cloud Spanner — Scalable, Strongly Consistent SQL

  • Spanner — Google's globally distributed, horizontally scalable relational database. Combines the scalability of NoSQL with ACID guarantees of a traditional RDBMS.
  • Strongly consistent — All reads return the most recent write. No "eventual consistency" lag. Even across global regions, reads are consistent. Uses TrueTime (Google's atomic clock infrastructure).
  • When to use — Financial systems, gaming leaderboards, global inventory — anything needing relational semantics at massive global scale.

Bigtable — NoSQL for Time-Series / IoT

  • Bigtable — Google's wide-column NoSQL database. Powers Google Search index, Gmail, and Google Maps. Open-source equivalent: Apache HBase.
  • Wide-column — Rows identified by a row key. Each row can have millions of columns. Very sparse — most columns in a row can be empty without wasting space.
  • Time-series data — Data points indexed by timestamp. Example: temperature sensor recording every second. Row key = sensorID + timestamp. Very efficient for range scans by time.
  • IoT = Internet of Things. Millions of devices sending continuous readings. Bigtable handles millions of writes per second with single-digit millisecond latency.

Firestore — NoSQL Document DB

  • Document DB — Data stored as documents (similar to JSON objects). Documents grouped into collections. No fixed schema — each document can have different fields.
  • Serverless — Automatically scales from zero to global traffic. Pay per read/write operation and GB stored.
  • For apps — Backend for mobile/web apps. Real-time listeners — when a document changes, all connected clients are instantly notified.
  • For metadata storage — In data engineering, Firestore stores pipeline metadata: job status, configuration, run history.

🎯 Workflow Orchestration

Coordinating multiple tasks in correct order — dependencies, retries, scheduling, notifications

GCP ServiceDescription / Use Case

Cloud Composer — DAG-based Orchestration

  • DAG-based — Workflows written as Directed Acyclic Graphs in Python. Each node = task (operator). Each edge = dependency. Visualised in Airflow's web UI as a graph or Gantt chart.
  • Supports complex scheduling: "run every Monday at 6 AM", "run when upstream DAG completes", "skip weekend runs".
  • When to use vs others — Composer for complex multi-step ETL with hundreds of tasks, retries, and a visual DAG UI. Too heavy for simple one-step scheduled tasks.

Cloud Scheduler — Cron-based Scheduling

  • Cloud Scheduler — Fully managed enterprise-grade cron job service. Schedule HTTP requests, Pub/Sub messages, or App Engine tasks at any frequency.
  • Cron = Unix/Linux time-based job scheduler. Cron expression: 0 2 * * * = "every day at 2:00 AM". Five fields: minute (0–59), hour (0–23), day of month (1–31), month (1–12), day of week (0–7). * = every.
  • When to use — Scheduler for simple "call this URL every hour" use cases. Much lighter and cheaper than Composer for single-step jobs.

Cloud Functions — Event-triggered Launcher

  • In the orchestration context: glue that reacts to events and triggers downstream jobs.
  • File upload trigger — New CSV lands in GCS → Cloud Function fires → starts a Dataflow job to process it.
  • Pub/Sub trigger — Message arrives in a topic → Cloud Function starts a Dataproc job or posts to Slack.
  • Stateless — Each invocation is independent. For complex stateful orchestration with retries and monitoring, use Composer or Workflows.

Workflows — Step-based Serverless Orchestration

  • Workflows — GCP's newer, fully serverless workflow orchestration service. Define pipelines as YAML or JSON steps. No Airflow needed — lighter and cheaper for simpler use cases.
  • Step-based — Each step is a named unit of work: call an HTTP endpoint, call a GCP API, assign a variable, loop, branch on conditions, handle errors.
  • Serverless — Pay per step execution. Scales to zero when idle — perfect for infrequent pipelines.
  • When to use — Workflows for simpler API-driven orchestration (call API A, then call API B, then write to BigQuery). Composer for complex multi-step ETL.

Column 1: Storage Class

A property set on a GCS bucket (or individual objects). Tells Google how to store your data — which hardware tier, how to replicate it, and how to price it. You can change the class of an object at any time using Object Lifecycle Management rules (automated policies that move data to cheaper tiers as it ages).

Column 2: Access Frequency

How often you expect to read (retrieve) the data. GCS does NOT enforce this — you can read Archive data daily — but you'll pay the high retrieval cost. Choose based on your expected real-world access pattern.

  • Frequent (Standard) — Multiple times per day, every day. Live application data, active datasets, files your pipeline reads constantly.
  • Monthly (Nearline) — Once a month or less. Monthly reporting data, ML training sets you retrain monthly, backups you restore rarely.
  • Quarterly (Coldline) — Once every 90 days. Disaster recovery files, compliance archives you occasionally audit.
  • Yearly (Archive) — Once a year or less. Legal records, historical logs kept for 7-year regulatory retention, raw data you never expect to touch again.

Column 3: Cost (Storage)

How much you pay per GB per month to store the data, regardless of whether you access it. The ongoing "parking fee."

Rule of thumb: Read data >1× per month → Standard. ~1×/month → Nearline. ~1×/quarter → Coldline. ~1×/year → Archive.

Column 4: Retrieval Cost

What you pay per GB when you READ (download) data from GCS — on top of network egress fees. The "cost to get the data back."

Trap to avoid: Storing infrequently accessed data in Standard (overpaying for storage) OR storing frequently accessed data in Archive (overpaying for retrieval). Match the class to your actual access pattern.

Column 5: Minimum Storage Duration

The minimum time GCS will bill you for storing an object, even if you delete it earlier. If you store a file in Coldline for 30 days then delete it, you are still billed for 90 days.

  • None (Standard) — No minimum. Store for 1 second, pay for 1 second. Full flexibility. No lock-in.
  • 30 days (Nearline) — Delete before 30 days → charged as if it stayed 30 days.
  • 90 days (Coldline) — Must keep data at least 90 days to avoid an early deletion charge.
  • 365 days (Archive) — Commit to storing data for a full year. Delete at day 100 → still pay for 365 days.

📖 Complete Glossary

Every key term from all 4 images — defined in one place

Apache Beam

Unified open-source SDK to build both batch and streaming pipelines. "Beam" = Batch + strEAM. Run on Dataflow, Spark, Flink.

Apache Spark

In-memory distributed data processing engine. Faster than Hadoop MapReduce. Supports SQL (Spark SQL), ML (MLlib), streaming (Structured Streaming), graph processing.

Apache Hadoop

Original big data framework: HDFS (storage) + YARN (resource manager) + MapReduce (batch compute). Disk-based, batch-only.

Apache Airflow

Open-source workflow orchestration platform. Write DAGs in Python to schedule and monitor tasks. Created by Airbnb in 2014. Managed version on GCP = Cloud Composer.

ETL

Extract → Transform → Load. Classic data engineering pattern: pull data from source, clean/enrich it, then write to destination.

ELT

Extract → Load → Transform. Modern pattern: load raw data first, then transform inside the warehouse (BigQuery) using SQL. Preferred when storage is cheap and SQL is powerful.

Batch Processing

Process a finite, bounded dataset in one job run. Has a clear start and end. Example: daily report generation over yesterday's records.

Stream Processing

Process an infinite, continuous flow of data as it arrives. No end. Example: live fraud detection on card transactions.

Serverless

No infrastructure to provision or manage. Cloud auto-scales and bills per usage. You only write and deploy code — no VMs, no clusters to start or stop.

Cluster-based

You provision a group of VMs (a cluster). You choose count and size. You manage its lifecycle. Example: Dataproc clusters. Billed even when idle.

Fully Managed

The cloud provider handles all operational tasks: installation, upgrades, monitoring, scaling, patching. You focus on code and logic, not infrastructure.

Auto-scaled

The system automatically adds or removes compute resources based on current load, without manual intervention. Dataflow auto-scales workers based on Pub/Sub backlog.

DAG

Directed Acyclic Graph. Nodes = tasks, edges = dependencies. Directed = one-way relationships. Acyclic = no cycles. Used in Airflow/Composer to define workflow order.

Topic (Pub/Sub)

A named channel in Pub/Sub to which publishers send messages. Subscribers don't connect to publishers — they connect to topics. Example: "orders", "sensor-readings".

Subscription (Pub/Sub)

A named resource representing interest in a topic. Each subscription receives all messages independently (fan-out). Each subscription = one consumer group.

Publisher

An application or service that creates and sends messages to a Pub/Sub topic. Does not know who the subscribers are. Decoupled from consumers.

Subscriber

An application or service that receives messages from a Pub/Sub subscription. Can pull (request messages) or be pushed (receive via HTTP endpoint).

Asynchronous

The sender does not wait for the receiver to process the message. Fire and forget. Enables loose coupling between services. The opposite of synchronous (waiting for a response).

Legacy Migration

Moving existing on-premises workloads (old Hadoop clusters) to the cloud with minimal code changes. Dataproc's primary strength.

PCollection

Beam's distributed dataset. Can be bounded (batch, finite) or unbounded (stream, infinite). Every Beam transformation takes PCollections as input and output.

PTransform

A data processing step in Apache Beam. ParDo (map/filter), GroupByKey (shuffle), Combine (reduce/aggregate), Flatten (merge multiple PCollections), Partition (split).

Orchestration

Coordinating when and how each step of a multi-step workflow runs. Defining: what runs when, in what order, what to do on failure, how many retries.

CDC

Change Data Capture. Watches the database's transaction log and captures only rows that changed (INSERT, UPDATE, DELETE) — without re-reading the entire table. Used by Datastream.

Data Lake

A storage repository holding vast amounts of raw data in native format until needed. Stores anything (structured, semi-structured, unstructured) without imposing a schema upfront. GCS is the data lake on GCP.

Data Warehouse

Stores and queries large volumes of historical, structured data for analytics and BI. Schema-on-write. Optimised for complex analytical queries. BigQuery is the data warehouse on GCP.

Columnar Storage

Data stored column-by-column (not row-by-row). Analytics queries that read a few columns from millions of rows are faster and cheaper. Used by BigQuery and Parquet format.

ACID Transactions

Atomicity (all or nothing), Consistency (data integrity rules always met), Isolation (concurrent transactions don't interfere), Durability (committed data persists). Property of relational DBs.

NoSQL

Not Only SQL. Schema-less or flexible-schema databases. No rigid table structure. Trade ACID transactions for horizontal scalability and performance. Examples: Bigtable, Firestore.

Wide-column DB

Data stored in rows identified by a row key. Each row can have millions of columns. Very sparse. Used by Bigtable. Efficient for range scans by row key (e.g., sensorID + timestamp).

Document DB

Data stored as JSON-like documents. Documents grouped into collections. No fixed schema — each document can have different fields. Used by Firestore.

Metadata

Data about data. Table name, schema (column names and types), owner, creation date, last modified, row count, description, tags, lineage. NOT the actual data rows.

Data Lineage

The full journey of data: where it was created, what transformations it went through, where it was used. Critical for debugging data quality issues and compliance audits.

PII

Personally Identifiable Information. Data that identifies a specific individual: name, email, phone, SSN. Must be tagged, access-controlled, and tracked under GDPR, HIPAA regulations.

Cron

Unix/Linux time-based job scheduler. Cron expression: 5 fields — minute, hour, day-of-month, month, day-of-week. Example: 0 2 * * * = every day at 2:00 AM. * = every.

Fan-out

One message published to a Pub/Sub topic is delivered to ALL subscriptions on that topic independently. Each subscription gets its own copy of every message.

Acknowledgement (ack)

After processing a Pub/Sub message, the subscriber sends an ack to confirm delivery. If the ack deadline expires without ack, Pub/Sub re-delivers the message (at-least-once delivery).

SNCA

Mnemonic for GCS storage classes in order from hot to cold: Standard · Nearline · Coldline · Archive. As you go S→A: storage gets cheaper, retrieval gets more expensive.

GCP / GCS

GCP = Google Cloud Platform. The full suite of Google cloud services. GCS = Google Cloud Storage. GCP's object storage service — store any file, accessed via URL.

📖 Every Column — Word by Word

Column 1: Function

All three are window functions (also called analytic functions) in SQL. A window function performs a calculation across a set of rows that are related to the current row — without collapsing them into a single output row like GROUP BY does. Syntax: FUNCTION() OVER (PARTITION BY col ORDER BY col)

  • OVER() — The keyword that makes it a window function. Without OVER(), RANK would not exist as a SQL function.
  • PARTITION BY — Resets the ranking for each group. Like GROUP BY but doesn't reduce rows. Example: rank students within each class (partition = class).
  • ORDER BY — Defines which column determines the rank order. Higher values first (DESC) = best score gets rank 1.

Column 2: Ties?

Ties = when two or more rows have the same value in the ORDER BY column. The question is: do RANK and DENSE_RANK handle ties by giving them the same rank number?

  • RANK() — Yes — If two rows tie, both get the same rank. Example: two rows with score 100 → both get rank 1.
  • DENSE_RANK() — Yes — Same as RANK for ties. Both tied rows get the same rank number.
  • ROW_NUMBER() — No — Does NOT handle ties. Every row gets a unique number. If two rows tie, the tie is broken arbitrarily (or by a secondary ORDER BY column you specify). No two rows share a row number.

Column 3: Skips Numbers?

Skips numbers = after a tie, does the next rank skip one or more integers?

  • RANK() — Yes (skips) — If 2 rows tie at rank 1, the next row gets rank 3 (not 2). The number 2 is skipped. If 3 rows tie at rank 1, the next row gets rank 4. The gap = number of tied rows.
  • DENSE_RANK() — No (never skips) — Even after a tie, the next rank is always the next consecutive integer. 2 rows tie at rank 1 → next row is rank 2. Always consecutive, always dense.
  • ROW_NUMBER() — No (never skips) — Numbers are always 1, 2, 3, 4... No skips, no ties. Sequential and gapless by definition.

Column 4: Unique?

Unique = does every row get a different number, guaranteed?

  • RANK() — No — Tied rows get the same number. Not unique in the presence of ties.
  • DENSE_RANK() — No — Tied rows get the same number. Not unique in the presence of ties.
  • ROW_NUMBER() — Yes — Every row gets a different number, always. Guaranteed unique across all rows in the partition. This makes it ideal for de-duplication and pagination.

Column 5: Definition

  • "Same rank, but gaps appear" (RANK) — Ties share a rank; the gap in numbering shows how many rows shared that rank. The total count of distinct rank values may be less than the total rows.
  • "Same rank, no gaps" (DENSE_RANK) — Ties share a rank; but the sequence of distinct rank values is always 1, 2, 3... without gaps. The highest rank value equals the number of distinct ranking values.
  • "Always assigns unique, sequential numbers, even for ties" (ROW_NUMBER) — The word "even" is key — ties do NOT get the same number. One tied row gets N, the next gets N+1. Sequential = 1, 2, 3, 4... no repeats, no gaps.

When to Use Which

Use RANK() when…

You want to show true competitive ranking where ties result in gaps. Example: Sales leaderboard — 2 people tied for 1st, next person is 3rd. The gap tells the user "two people beat you." Sports rankings, exam results.

Use DENSE_RANK() when…

You want tied items to share a rank but prefer clean, gap-free numbering. Example: "Top 3 product categories by sales" — you always want exactly 3 distinct rank levels, even if multiple products tie at each level.

Use ROW_NUMBER() when…

You need exactly one row per number — for de-duplication, pagination (LIMIT per page), or picking the latest record per group. Example: "Get the most recent order per customer" — partition by customer_id, order by order_date DESC, then WHERE row_num = 1.

Common SQL Pattern — De-duplication with ROW_NUMBER()

-- Get latest record per customer (most common interview question) WITH ranked AS (   SELECT *,     ROW_NUMBER() OVER (       PARTITION BY customer_id       ORDER BY order_date DESC     ) AS rn   FROM orders ) SELECT * FROM ranked WHERE rn = 1; -- Top N per group (e.g. top 3 products per category) WITH ranked AS (   SELECT *,     DENSE_RANK() OVER (       PARTITION BY category       ORDER BY revenue DESC     ) AS dr   FROM products ) SELECT * FROM ranked WHERE dr <= 3;

📖 Every Word in the Decision Table — Explained

Situation 1: "Typos or non-critical corrections" → Type 1 (Overwrite)

  • Typos — A data entry mistake. Example: customer name saved as "Jhon" instead of "John". The wrong value was never valid — it was always meant to be "John". There is no business value in keeping "Jhon" in history.
  • Non-critical corrections — Changes to attributes that the business does not need to track over time. "Non-critical" = the old value has zero analytical importance. Example: a product's internal code was updated for consistency, an employee's middle name was added, a phone number format was standardised.
  • Why Type 1 fits — Since the old value was either wrong or irrelevant, overwriting it causes no loss of meaningful information. Using Type 2 here would create unnecessary extra rows for data that was never business-valid.
  • Key signal — Ask: "Would an analyst ever want to report on the old value?" If No → Type 1.

Situation 2: "Need full audit/history of changes" → Type 2 (Add New Row)

  • Full audit — An audit is a formal review of historical records to verify accuracy, detect fraud, or meet compliance requirements. "Full" = every single change must be traceable, not just the most recent one.
  • History of changes — A complete chronological record of every value a dimension attribute has ever held. Example: an employee moved through departments — Engineering (2018), Marketing (2020), Sales (2022). All three states must be queryable.
  • Why Type 2 fits — Each change creates a new row with its own surrogate key, effective_start_date, effective_end_date, and is_current flag. The fact table stores surrogate keys — so joining gives the EXACT value at the time of each transaction. Perfect historical accuracy for any point in time.
  • Key signal — Ask: "Do I need to know what this value was at the exact time of a past transaction?" If Yes → Type 2.

Situation 3: "Only care about current and previous values" → Type 3 (Add New Column)

  • Only care about — This phrase is the key qualifier. It means you have deliberately scoped your business requirement to just two states — now and immediately before. You are NOT trying to answer "what was it in 2019?" — only "what was it last time, and what is it now?"
  • Current values — What the attribute is today. The active, live value used for current reporting. Stored in the current_value column.
  • Previous values — What the attribute was immediately before the most recent change. Stored in the previous_value column. Only one step back — the version before that is gone once another change happens.
  • Why Type 3 fits — Adds extra columns without adding rows. Simple to implement, easy to query. No surrogate keys, no date ranges. Just: WHERE did this customer used to be, and WHERE are they now?
  • Key signal — Ask: "Do I only need to compare today vs. the last change, with no need to go further back?" If Yes → Type 3. Example: reporting customers who moved sales region last quarter.

Situation 4: "Separate historical and active storage" → Type 4 (History Table)

  • Separate — Two physically different database tables are used. The word "separate" is the defining characteristic of Type 4. History is not mixed into the main dimension table.
  • Historical storage — A dedicated table (e.g., dim_customer_history) that stores every past version of the dimension record with timestamps. Can grow very large over time. Queried less frequently — usually for audits, compliance, or analytical deep-dives.
  • Active storage — The main dimension table (e.g., dim_customer) that stores only ONE row per entity — the current, live values. Always small and fast. Queried constantly by operational dashboards and ETL joins.
  • Why Type 4 fits — Keeps the main dimension table small and performant for high-frequency lookups. If you stored all history in the main table (Type 2), every query would need a WHERE is_current = True filter and performance degrades as history grows. Type 4 avoids this by physically separating the two concerns.
  • Key signal — Ask: "Is the main dimension table used for high-performance current lookups AND do I also need a full audit trail separately?" If Yes → Type 4.

Situation 5: "Some attributes change fast — isolate them" → Type 5 (Mini-Dimension + Outrigger)

  • Mini-dimension — A small separate dimension table that contains a subset of attributes that change frequently. Instead of cluttering the main dimension with rapidly-changing columns, you extract those columns into their own tiny "mini" dimension. Example: a Customer dimension might have stable attributes (name, DOB) but fast-changing attributes (income band, credit score tier, loyalty tier). The fast-changing ones go into a dim_customer_profile mini-dimension.
  • Outrigger — A foreign key column added to the MAIN dimension table (Type 1 — always overwritten to current) that points to the CURRENT row in the mini-dimension. It is called an "outrigger" because it hangs off the side of the main dimension like an outrigger on a boat.
  • How it works — The fact table stores TWO foreign keys: (1) the main dimension surrogate key (for historical joins to stable attributes) and (2) the mini-dimension key (for joins to fast-changing attributes at the time of the transaction). The main dimension's outrigger column always shows the current mini-dimension key (Type 1 overwrite).
  • Why it exists — Without Type 5, adding a fast-changing attribute to a Type 2 dimension would create a new row every time that attribute changes — even if the core attributes (name, address) haven't changed. This bloats the dimension with millions of rows. Type 5 isolates fast-changing attributes so they don't trigger unnecessary Type 2 row creation in the main dimension.
  • Key signal — Ask: "Does this dimension have a mix of slow-changing and fast-changing attributes, and are the fast-changing ones causing row explosion in my Type 2 dimension?" If Yes → Type 5.

Situation 6: "Need both historical AND current-state view" → Type 7 (Dual Type 1 + Type 2)

  • Dual — Two mechanisms run simultaneously on the same dimension. Type 7 is unique because it stores BOTH a surrogate key (for historical accuracy) AND a natural/durable key (for current-state lookup) in the fact table itself.
  • Surrogate key (Type 2 component) — The artificial key (e.g., customer_sk = 1001 for "Alice when she was in Mumbai"). The fact table stores this surrogate key at transaction time. Joining via surrogate key gives you the HISTORICAL value — what the attribute was when the transaction happened.
  • Natural / Durable key (Type 1 component) — The original business identifier (e.g., customer_id = 101 for "Alice" regardless of which city she lives in). The fact table also stores this natural key. Joining via the natural key to a "current dimension view" (a SQL view filtered to WHERE is_current = True) gives you the CURRENT value — what the attribute is today, applied to all historical transactions.
  • Two views from one fact table — An analyst can write two different queries on the same fact table:
    • Join via customer_sk → "What city was Alice in when she placed this order?" (historical)
    • Join via customer_id to current view → "What city is Alice in now, and how many orders has she ever placed?" (current state applied to all history)
  • Why it's powerful — No other SCD type lets you answer both questions from the same fact table without reformulating the query. Type 2 alone can only give historical. Type 1 alone can only give current. Type 7 gives BOTH simultaneously.
  • Key signal — Ask: "Do my analysts need to report on both what-the-value-was-at-the-time AND what-the-value-is-today, using the same fact table?" If Yes → Type 7. This is common in sales reporting (historical territory vs. current territory) and finance (historical cost centre vs. current cost centre).

📖 Every Column from the Table — Word by Word

Column 1: SCD Type

SCD = Slowly Changing Dimension. A type is a numbered strategy (0–6) that describes HOW you handle a change to a dimension value. Each type is a different design choice with different tradeoffs between simplicity, storage, and historical accuracy. The type you choose determines your entire data model for that dimension table.

  • Why no Type 5? — Type 5 exists in theory (mini-dimension + Type 1 outrigger) but is rarely discussed or used in practice. The common types are 0, 1, 2, 3, 4, and 6.
  • Why Type 6 = 1+2+3? — Literally 1+2+3=6. It combines all three strategies into one powerful hybrid approach.

Column 2: Behavior

Behavior = what physically happens to the database when a dimension value changes in the source system. This is the action your ETL pipeline takes:

  • "No change allowed" (Type 0) — The ETL pipeline detects a change but intentionally does nothing. The original value is frozen in the warehouse forever. The source change is discarded.
  • "Overwrite old data" (Type 1) — The ETL pipeline runs an SQL UPDATE on the existing row. The old value is replaced in-place. After the update, the old value no longer exists anywhere in the warehouse.
  • "Add a new row (track history)" (Type 2) — The ETL pipeline runs an SQL UPDATE on the old row (set end_date and is_current=False) AND an SQL INSERT for the new row (new surrogate key, new value, start_date=today, is_current=True). Both rows coexist forever.
  • "Add new column (partial history)" (Type 3) — The ETL pipeline runs an SQL UPDATE that moves the current value into the previous_value column and writes the new value into the current_value column. Only two versions visible at any time.
  • "Historical table + current table" (Type 4) — The ETL pipeline runs an UPDATE on the main dimension table (always stores current only) AND an INSERT into a separate history table (stores all versions with timestamps).
  • "Hybrid of 1 + 2 + 3" (Type 6) — The ETL pipeline inserts a new row (Type 2 behavior) AND overwrites the current_value column on ALL rows for that entity (Type 1 behavior) AND maintains a historical_value column on each row (Type 3 behavior). Most complex ETL logic of all types.

Column 3: Use Case

Use case = the real-world business scenario where this SCD type is the right choice.

  • "Immutable fields like DOB" (Type 0) — DOB = Date of Birth. Some attributes should logically never change. If a source system "corrects" a date of birth, you might deliberately ignore that change and keep the original. Other examples: original account open date, first transaction date, country of origin at registration. These are "point-in-time" facts, not attributes that evolve.
  • "Fix typos or non-critical info" (Type 1) — When a value was entered incorrectly (e.g., customer name "Jon" should be "John") and historical accuracy about that typo has zero business value. Also for attributes that are simply not important to track historically — like a customer's email address (analysts only care about the current one, not every old email).
  • "Track full historical changes" (Type 2) — When the business genuinely needs to know "what was the value at the time of this transaction?" Example: a customer changed their loyalty tier from Silver to Gold. All orders placed while Silver should be analysed under Silver. Orders after Gold promotion should be under Gold. Full audit trail required.
  • "Keep limited history (e.g., last address)" (Type 3) — When the business only needs "current vs. previous" for comparison. Example: "Show me customers who changed region in the last reorganisation" — you just need current_region and previous_region. No need to go back further than one change.
  • "Separate table for history" (Type 4) — When the main dimension table is used heavily for current-state lookups (must be small and fast) but a separate audit/history requirement exists. The main table stays lean; the history table satisfies compliance or audit queries. Example: employee current department (fast lookup) + all past departments (compliance audit).
  • "Advanced use cases" (Type 6) — Complex enterprise reporting that needs: (a) historical accuracy in fact table joins, (b) easy "what is it today?" lookups without filtering, and (c) ability to compare current vs. historical in the same query. Used when you have both operational reporting (current state) and analytical reporting (historical accuracy) on the same dimension.

Column 4: Data Preserved?

Data Preserved = does the warehouse retain a record of what the value was BEFORE the change? Can you query the old value after the update?

  • ✓ Yes (Type 0) — The original value is preserved forever — because nothing ever changes. The "preservation" here is by inaction. If the source changes, the warehouse doesn't follow → original value is permanently preserved.
  • ✗ No (Type 1) — The old value is completely overwritten and unrecoverable. After an UPDATE, the old value is gone from the warehouse. No row in any table stores it. This is the only type where data is permanently destroyed.
  • ✓ Yes (Type 2) — The old row still exists with the old value, its surrogate key, and the date range it was active. Full history is preserved. You can query any point in time and see the exact value at that moment.
  • Partially (Type 3) — Only the immediately previous value is preserved (in the previous_value column). If the value changes twice, the first version is lost. So partial = limited history (one step back only).
  • ✓ Yes — in separate table (Type 4) — The current dimension table does NOT preserve history (it only has the current row). But the history table preserves all old values. So history IS preserved — just in a different table, not the main dimension table.
  • ✓ Yes (Type 6) — Full history is preserved via new rows (Type 2 component). Every version of a dimension value has its own row with start/end dates. The historical_value column on each row also shows what that row's value was at the time.

What is a Slowly Changing Dimension?

In a data warehouse, a dimension is a descriptive table (Customer, Product, Employee, Location). Over time, the values in these tables change slowly — a customer moves cities, a product gets re-categorised, an employee changes department. The question is: how do you handle that change? Do you overwrite the old value, keep history, or add a new column? The answer determines your SCD type.

Key principle: In a fact table (orders, transactions, events), you want to know what the dimension value WAS at the time of the event — not what it is today. Example: a customer placed an order when they lived in Mumbai. They later moved to Delhi. The order record should still show Mumbai. SCD types determine whether this historical accuracy is preserved.

Type 0 — Retain Original (Freeze)

Strategy: Ignore all changes. The original value is kept forever, no matter what happens in the source system.

How it works

When a change is detected in the source, it is discarded. The dimension row is never updated.

  • Retain Original — "Retain" = keep. "Original" = the first value that was loaded. No future writes happen to this row.
  • Useful for attributes that are inherently immutable or where the warehouse intentionally captures the value at first load.

Example

Customer loaded in 2020: original_city = "Mumbai" Customer moves to Delhi in 2023 → Source updates to Delhi Type 0: Warehouse IGNORES the update → still stores "Mumbai" Use case: "City where customer first registered" — intentionally frozen.

When to use

Date of birth, original registration country, signup date, immutable identifiers. When you deliberately want the "as of first seen" value and NOT current reality.

Type 1 — Overwrite (No History)

Strategy: When a value changes, simply overwrite the old value with the new one. History is permanently lost.

How it works

The existing row in the dimension table is UPDATEd in-place. The old value is gone. No new rows are created.

  • Overwrite — The old value is replaced. Like editing a cell in a spreadsheet — the previous content disappears.
  • Simplest SCD type to implement. No extra columns, no extra rows, no date tracking.
  • All historical fact records that join to this dimension will now see the NEW value, even for old transactions.

Example — Before and After

customer_idnamecity
101AliceMumbai (old)

After Type 1 update (Alice moves to Delhi):

customer_idnamecity
101AliceDelhi (new, old value gone)
Problem: Any fact table row (order placed when Alice was in Mumbai) now joins to Delhi. The historical accuracy is permanently destroyed. All old orders now look like they came from Delhi.

When to use

Fixing data quality errors (typos, wrong codes), or attributes where historical accuracy simply doesn't matter to your business. Example: correcting a misspelled product name, or updating a phone number.

Type 2 — Add New Row (Full History) ⭐ Most Common

Strategy: When a value changes, INSERT a new row for the new value and mark the old row as expired. Both rows coexist — full history preserved.

How it works

  • A surrogate key (artificial unique key, e.g., customer_sk) is added to the dimension table — separate from the natural/business key (customer_id).
  • When a change occurs: the old row gets an expiry date (effective_end_date) and a flag (is_current = False). A NEW row is inserted with the new value, a new surrogate key, and effective_start_date = today.
  • The fact table stores the surrogate key at the time of the transaction — so joining gives the value as it was at that time.

Key columns added

  • surrogate_key (sk) — Unique artificial key. Each version of a customer gets its own sk.
  • natural_key (customer_id) — The original business identifier. Same across all versions of the same customer.
  • effective_start_date — The date this row's values became effective.
  • effective_end_date — The date this row's values stopped being current. NULL or 9999-12-31 means "still current."
  • is_current (flag) — Boolean. True = this is the active record. False = expired version.

Example — Alice moves from Mumbai to Delhi

1002101Alice Delhi 2023-07-01 9999-12-31 True (current)
Result: An order placed in 2021 (fact row storing customer_sk = 1001) → joins to Mumbai ✓. An order placed in 2024 (fact row storing customer_sk = 1002) → joins to Delhi ✓. Full historical accuracy preserved.

When to use

The DEFAULT choice for most slowly changing dimensions. Use when historical accuracy matters for reporting. Customer demographics, employee department, product category — any attribute that changes and where you need to know "what was it at the time?"

Type 3 — Add New Column (Partial History)

Strategy: Add a "previous_value" column alongside the current value column. Only tracks one version back.

How it works

  • When a change occurs, the current value is moved into a previous_value column, and the new value is written into the current_value column. No new rows. No new tables. Just extra columns.
  • You can only see the last two states: what it is NOW and what it was BEFORE the most recent change. If the value changes again, the "before" version is permanently lost.

Example — Alice moves from Mumbai to Delhi

customer_idnameprevious_citycurrent_city
101AliceMumbaiDelhi
Limitation: If Alice later moves from Delhi to Bangalore, the row becomes: previous_city = Delhi, current_city = Bangalore. Mumbai is now permanently lost. Type 3 only gives you one step of history.

When to use

When you only need to compare current state vs. the immediately previous state. Example: reporting that shows "this quarter vs. last quarter region," or tracking an employee's current department vs. their previous one — with no need for the full history.

Type 4 — History Table (Mini-Dimension)

Strategy: Keep current values in the main dimension table. Store ALL historical changes in a separate history table.

How it works

  • The main dimension table (dim_customer) always has just one row per customer — containing current values only. Fast and simple to query for current state.
  • A separate history table (dim_customer_history) stores all changes with timestamps. Every time a value changes, a new row is inserted into the history table.
  • The fact table can join to either: the main table (for current reporting) or the history table (for historical analysis).

Example

dim_customer (current only): 101 | Alice | Delhi | 2024-01-01 dim_customer_history (all versions): 101 | Alice | Mumbai | 2020-01-01 | 2023-06-30 101 | Alice | Delhi | 2023-07-01 | NULL (current)

When to use

When the main dimension table needs to stay lean for performance (fast lookups of current state), but you still want full history available for audit or analysis. Common in OLTP→OLAP migrations where the operational system only stores current state.

Type 6 — Hybrid (Type 1 + 2 + 3 combined)

Strategy: Combines all three approaches — new rows like Type 2, current/previous columns like Type 3, and overwrites current_value across all rows like Type 1.

Why "Type 6"? 1 + 2 + 3 = 6. It is literally the sum of Types 1, 2, and 3 combined into one approach.

How it works

  • Like Type 2: a new row is inserted when a value changes, with effective_start_date, effective_end_date, is_current columns.
  • Like Type 3: each row has a current_value column AND an original_value column (or previous_value).
  • Like Type 1: the current_value column is OVERWRITTEN on ALL rows for that customer — even old expired rows — to always reflect what the current value is today.

Example — Alice: Mumbai → Delhi → Bangalore

Notice: current_city = Bangalore on ALL rows — even the expired Mumbai and Delhi rows. This lets reports always show "where is Alice now?" without filtering to is_current=True first. But historical_city preserves what city was used at the time of each version.

When to use

When you need the richest possible dimension — full history AND the ability to easily report "current state across all history." Common in enterprise data warehouses where analysts need both "what was it then?" and "what is it now?" in the same query without complex joins.

Type 5 — Mini-Dimension + Type 1 Outrigger

Strategy: Extract fast-changing attributes into a separate mini-dimension table. The main dimension holds a Type 1 (always-current) foreign key pointing to it.

The Problem Type 5 Solves

In a Type 2 dimension, every change to ANY attribute creates a new row. If a Customer dimension tracks both name/address (change rarely) and income band/credit tier (change frequently), the frequent changes explode the dimension with millions of rows — even though nothing important changed about the customer.

Solution: Separate fast-changing attributes into a small mini-dimension (dim_customer_profile). The main dim_customer only gets a new row when stable attributes change. The mini-dimension gets a new row when fast attributes change.

Key Components

  • Main dimension (dim_customer) — Contains stable, slow-changing attributes: name, DOB, gender, address. Uses Type 2 (new rows when these change). Has a current_profile_key outrigger column (Type 1 — always overwritten to current mini-dim key).
  • Mini-dimension (dim_customer_profile) — Contains fast-changing attributes: income band, credit score tier, loyalty status, age group. Each unique combination of these values gets one row. New row added when combination changes.
  • Fact table — Stores BOTH customer_sk (from main dim) AND profile_key (from mini-dim) at transaction time. This preserves both stable and fast-changing attribute history independently.
  • Outrigger — The current_profile_key column in the main dimension is the outrigger. It is always Type 1 (overwritten) to point to the customer's current profile. Used for current-state reporting without joining the fact table.

Example

dim_customer (main): customer_sk | customer_id | name | city | current_profile_key 1001 | 101 | Alice | Mumbai | 55 ← always current (Type 1) dim_customer_profile (mini): profile_key | income_band | credit_tier | loyalty_status 50 | Low | Bronze | Basic 55 | Medium | Silver | Premium ← Alice's current profile fact_orders: order_id | customer_sk | profile_key | amount 9001 | 1001 | 50 | 500 ← Alice was Low/Bronze when ordered 9002 | 1001 | 55 | 1200 ← Alice was Medium/Silver when ordered

Data Preserved?

Yes — in the mini-dimension. Each profile combination has its own key stored in the fact table, so you can always see what profile state existed at transaction time.

When to Use

When a dimension has a mix of slow-changing (stable) and fast-changing attributes, and the fast-changing ones are causing Type 2 row explosion. Common for customer demographics, credit scoring, or any profile-based segmentation that updates frequently.

Type 7 — Dual Type 1 + Type 2 (Surrogate + Natural Key in Fact)

Strategy: Store BOTH a surrogate key (Type 2, for historical joins) AND a natural/durable key (Type 1, for current-state joins) in the fact table. Enables two different analytical views of the same data.

The Core Idea

All other SCD types force you to choose: historical accuracy OR current-state simplicity. Type 7 refuses to choose — it gives both simultaneously by storing two keys in the fact table and providing two SQL views on the same dimension table.

Key Components

  • Dimension table — Uses Type 2 structure: surrogate key, natural key, attribute values, effective_start_date, effective_end_date, is_current flag. Same as a standard Type 2 dimension.
  • Current dimension view — A SQL view defined as: SELECT * FROM dim_customer WHERE is_current = TRUE. This view always shows only the latest row per customer. Used for current-state joins.
  • Fact table — Stores TWO foreign keys:
    • customer_sk — The surrogate key at the time of the transaction (Type 2 key). Points to a specific historical version.
    • customer_id — The natural/durable business key. Same for all versions of the same customer. Points to whichever row is current in the current view.

Two Queries, Two Answers from One Fact Table

-- HISTORICAL VIEW: What city was the customer in when each order was placed? SELECT f.order_id, d.city, f.amount FROM fact_orders f JOIN dim_customer d ON f.customer_sk = d.customer_sk; -- Result: order 9001 → Mumbai, order 9002 → Delhi (historically accurate) -- CURRENT-STATE VIEW: Apply today's city to ALL historical orders SELECT f.order_id, v.city, f.amount FROM fact_orders f JOIN dim_customer_current_view v ON f.customer_id = v.customer_id; -- Result: ALL orders → Delhi (Alice's current city applied to all history)

Why Both Keys?

  • Surrogate key (customer_sk) — Frozen at transaction time. Joining via this key always returns the dimension row that was active WHEN the fact row was created. Perfect for "what was the value at the time?"
  • Natural key (customer_id) — The same ID across all versions. Joining via this key to the current view always returns TODAY's dimension row. Perfect for "what is the value now, across all history?"
  • No data duplication — The dimension table itself is NOT duplicated. Only the fact table stores an extra key column. The overhead is minimal.

Data Preserved?

Yes — full history is preserved via the Type 2 surrogate key structure. Additionally, current state is always accessible via the natural key + current view. Best of both worlds.

When to Use

When analysts need to run both historical reports ("what territory was this rep in when they made this sale?") AND current-state reports ("how many total sales has this rep made, using their current territory?") against the same fact table. Very common in sales, finance, and HR analytics.

🗃️ What is a Database?

An organised collection of structured data managed by a DBMS. Designed for OLTP — fast, frequent, small reads and writes by live applications.

Definition — word by word

  • Database — "Data" = information. "Base" = a foundation or store. A database is the persistent store that an application reads from and writes to, keeping data structured and consistent.
  • DBMS = Database Management System — the software (MySQL, PostgreSQL) that sits between your application and the raw data files, handling querying, indexing, transactions, and access control.
  • OLTP = Online Transaction Processing. "Online" = happening in real time, as users interact with the application. "Transaction" = a unit of work (e.g., one order placed, one payment processed). "Processing" = executing that work immediately.
  • ACID = Atomicity (all-or-nothing), Consistency (data integrity always maintained), Isolation (concurrent transactions don't interfere), Durability (committed data survives crashes). Databases guarantee ACID for every transaction.

Database Tools — Every Word

  • MySQL — "My" = named after the daughter (Mya) of co-creator Michael Widenius. "SQL" = Structured Query Language. World's most popular open-source RDBMS (Relational Database Management System). Rows and columns, ACID transactions, foreign keys. Used by: Facebook (originally), Twitter, WordPress, YouTube. On GCP: managed as Cloud SQL for MySQL.
  • PostgreSQL — "Post" = successor to an older database called Ingres (also called POSTGRES historically, the "Post" means "coming after" Ingres). "GRES" = from Ingres. "SQL" added when it adopted the SQL standard. Often called "Postgres." Open-source, standards-compliant, feature-rich RDBMS. Supports JSON, arrays, full-text search, custom data types, window functions, stored procedures, extensions. Preferred by engineers for correctness and extensibility. On GCP: Cloud SQL for PostgreSQL or AlloyDB.
  • SQL Server — Full name: Microsoft SQL Server. Microsoft's commercial (proprietary, not open-source) RDBMS. "SQL" = Structured Query Language. "Server" = runs as a server process, not embedded. Used heavily in enterprise Windows environments, .NET applications, and legacy enterprise systems. Tight integration with Microsoft tools (Excel, Power BI, Azure Data Factory, SSRS, SSAS). On GCP: managed as Cloud SQL for SQL Server.
  • MongoDB — "Mongo" = from "humongous" (designed for huge datasets that don't fit in traditional relational structures). A NoSQL document database. "Document" = data stored as BSON (Binary JSON) documents — like JSON objects with field-value pairs, nested objects, and arrays. "Schema-less" = each document in a collection can have completely different fields. No JOIN operations (joins are done in application code or with $lookup pipeline). Scales horizontally (sharding). Used for: content management, user profiles, catalogs, real-time personalisation. On GCP: use MongoDB Atlas (available on GCP Marketplace) or Firestore as the native equivalent.

🏭 What is a Data Warehouse?

A centralised repository for large volumes of historical, structured data from multiple source systems, optimised for complex analytical queries and BI reporting. OLAP workloads. SCD types apply here.

Definition — word by word

  • Data Warehouse — "Data" = information. "Warehouse" = a large storage facility. A data warehouse stores data from many different source systems (databases, SaaS tools, event streams) in one place for analysis. Like a physical warehouse that receives goods from multiple suppliers and stores them for distribution.
  • Centralised — All analytical data lives in one system. No need to query 10 different databases — analysts query one warehouse. Single source of truth.
  • Historical — Data warehouses keep ALL historical data, not just the current state. 5 years of transaction history, not just today's records. This is WHY SCD types exist — to handle how dimension values change over that historical period.
  • OLAP = Online Analytical Processing. "Online" = interactive queries. "Analytical" = complex queries scanning large amounts of data for insights (not updating a row). "Processing" = computing aggregations, trends, comparisons across millions of rows.
  • Star schema — A data warehouse design pattern. One central fact table (stores measurements/events like orders, transactions) surrounded by dimension tables (descriptive context like Customer, Product, Date, Location). The shape looks like a star. SCD types determine how dimension tables handle changes.
  • Snowflake schema — A variation of star schema where dimension tables are further normalised (split into sub-dimensions). More normalised = less redundancy but more JOINs. The shape looks like a snowflake.

Data Warehouse Tools — Every Word

  • BigQuery — Google Cloud's fully managed, serverless data warehouse. "Big" = designed for big data at petabyte scale. "Query" = its primary purpose is querying (not operational transactions). No cluster to manage — write SQL and BigQuery distributes across thousands of internal nodes automatically. Columnar storage (Capacitor format) = data stored column-by-column, not row-by-row → analytics that read a few columns from billions of rows are fast and cheap. Separates storage from compute = you pay for storage separately from query execution. Pay per TB scanned (on-demand) or per slot reservation (capacity pricing). Native integration with Dataflow, Datastream, Pub/Sub, Looker. The primary data warehouse on GCP.
  • Snowflake — A cloud-native data warehouse available on AWS, GCP, and Azure. Named after its unique architecture — like a snowflake, intricate and unlike any other. Key innovation: three-layer architecture — (1) Storage layer (data files in S3/GCS/Azure Blob), (2) Compute layer (virtual warehouses — independent clusters that execute queries), (3) Cloud services layer (metadata, query optimisation, security, access control). Each layer scales independently. Auto-suspend = virtual warehouses pause automatically when idle → you don't pay for idle compute. Multi-cluster shared data = multiple compute clusters can query the same data simultaneously without contention. Supports VARIANT data type for semi-structured data (JSON, Avro, Parquet) natively. Very popular in multi-cloud organisations. Direct BigQuery competitor.
  • Redshift — Amazon Web Services (AWS) data warehouse. "Red" = Amazon's brand colour (the Amazon logo arrow/smile is red). "Shift" = shifting massive data workloads to the cloud. A columnar MPP (Massively Parallel Processing) data warehouse. Architecture: Leader node (receives queries from clients, parses, creates execution plan, coordinates results) + Compute nodes (execute the query in parallel, each holding a slice of data). Data is stored on the compute nodes (storage and compute are coupled — unlike Snowflake/BigQuery). Redshift Serverless = newer option, no cluster management. Tight AWS ecosystem integration: S3, AWS Glue (ETL), AWS Lambda (triggers), QuickSight (BI). Main competitor to BigQuery and Snowflake, but AWS-native.

📖 Every Function — Word by Word

TRIM() — Remove spaces/chars from BOTH ends

  • TRIM = to cut away excess. Like trimming the edges of a piece of paper.
  • By default removes leading (before) and trailing (after) spaces. Can also remove a specific character: TRIM('*' FROM '***Raj***') → Raj.
  • Why use it? — User input often has accidental spaces. 'Raj ' and 'Raj' are NOT equal in SQL — TRIM normalises them so comparisons work correctly.
  • Example: WHERE name = TRIM(input_value) — prevents missed matches due to whitespace.

LTRIM() — Remove spaces from LEFT side only

  • L = Left. TRIM = remove. Only removes spaces (or a specified character) from the LEFT/beginning of the string. Right side is untouched.
  • LTRIM(' Raj') → 'Raj'. LTRIM('Raj ') → 'Raj ' (trailing spaces kept).
  • Useful when data has consistent left-padding that needs removal, but right formatting must be preserved.

RTRIM() — Remove spaces from RIGHT side only

  • R = Right. TRIM = remove. Only removes spaces (or a specified character) from the RIGHT/end of the string. Left side is untouched.
  • RTRIM('Raj ') → 'Raj'. RTRIM(' Raj') → ' Raj' (leading spaces kept).
  • Commonly used to clean exported fixed-width text files where every field is right-padded with spaces to a fixed length.

UPPER() — Convert to UPPERCASE

  • Converts every character in the string to its uppercase equivalent. 'sql' → 'SQL'. 'Hello World' → 'HELLO WORLD'.
  • Non-alphabetic characters (numbers, spaces, punctuation) are unaffected.
  • Common use: Case-insensitive comparison — WHERE UPPER(name) = UPPER('raj') matches 'Raj', 'RAJ', 'raj', etc.

LOWER() — Convert to lowercase

  • Converts every character to its lowercase equivalent. 'SQL' → 'sql'. 'Hello World' → 'hello world'.
  • Common use: Normalise emails — LOWER(email) ensures 'Raj@Gmail.COM' and 'raj@gmail.com' are treated as the same.

INITCAP() — Capitalize First Letter of Each Word

  • INIT = initial. CAP = capitalize. Capitalizes the first letter of each word and lowercases the rest.
  • INITCAP('raj damade') → 'Raj Damade'. INITCAP('SQL IS GREAT') → 'Sql Is Great'.
  • A "word" is any sequence of characters preceded by a space or non-alphanumeric character.
  • Not available in all databases: works in Oracle, PostgreSQL. In MySQL, combine UPPER + LOWER + SUBSTRING manually.

REPLACE() — Replace a Substring

  • Syntax: REPLACE(string, old_substring, new_substring)
  • Finds every occurrence of old_substring in string and replaces it with new_substring.
  • REPLACE('AB-CD', '-', ',') → replaces the hyphen with a comma → 'AB,CD'. Wait — image shows ABCD (the comma is used as separator in the args, the actual result replaces '-' with ',' giving 'AB,CD' or removes it giving 'ABCD' depending on the third arg being empty).
  • To DELETE a substring: use empty string as third arg — REPLACE('AB-CD', '-', '') → 'ABCD'.
  • Common use: Remove unwanted characters (REPLACE(phone, '-', '') removes all hyphens from phone numbers), fix encoding issues, standardise separators.

LPAD() — Pad Left Side

  • L = Left. PAD = add characters. Adds padding to the LEFT of a string until it reaches the target length.
  • Syntax: LPAD(string, total_length, pad_character)
  • LPAD('123', 5, '*') → total length = 5, string is 3 chars, so 2 stars added on left → '**123'.
  • If the string is already longer than total_length, it is truncated from the right.
  • Common use: Format numbers with leading zeros — LPAD(invoice_number, 8, '0') → '00000042'. Used in fixed-width report formatting, ID number generation.

RPAD() — Pad Right Side

  • R = Right. PAD = add characters. Adds padding to the RIGHT of a string until it reaches the target length.
  • Syntax: RPAD(string, total_length, pad_character)
  • RPAD('Raj', 6, '*') → total length = 6, string is 3 chars, so 3 stars added on right → 'Raj***'.
  • Common use: Fixed-width text file generation, right-padding labels for alignment in reports.

📖 Every Function — Word by Word

ROUND() — Round to N decimal places

  • Syntax: ROUND(number, decimal_places)
  • Rounds the number to the specified number of decimal places using standard rounding rules: if the next digit is ≥ 5, round up; if < 5, round down.
  • ROUND(123.456, 2) → looks at the 3rd decimal (6 ≥ 5) → rounds up the 2nd decimal → 123.46
  • ROUND(123.454, 2) → looks at the 3rd decimal (4 < 5) → keeps 2nd decimal → 123.45
  • ROUND(123.456, 0) → rounds to nearest integer → 123
  • ROUND(123.456, -1) → rounds to nearest 10 → 120
  • Common use: Financial calculations (round to 2 decimal places for currency), display formatting, reducing floating-point precision errors.

CEIL() — Always Round UP (Ceiling)

  • CEIL = ceiling. The ceiling is above you — CEIL always goes UP to the next integer, no matter how small the decimal part.
  • CEIL(12.3) → rounds UP to 13 (even though it's closer to 12)
  • CEIL(12.9) → 13. CEIL(12.0) → 12 (already an integer). CEIL(-12.3) → -12 (towards zero = up for negatives).
  • Also called: CEILING() in SQL Server and MySQL. CEIL() in Oracle, PostgreSQL, BigQuery.
  • Common use: Calculating pages needed (CEIL(total_rows / page_size)), billing (always charge full unit), time calculations (always round up to next hour).

FLOOR() — Always Round DOWN (Floor)

  • FLOOR = floor. The floor is below you — FLOOR always goes DOWN to the previous integer, discarding the decimal.
  • FLOOR(12.9) → rounds DOWN to 12 (even though it's closer to 13)
  • FLOOR(12.1) → 12. FLOOR(12.0) → 12. FLOOR(-12.3) → -13 (away from zero = down for negatives).
  • FLOOR vs ROUND: ROUND(12.9, 0) = 13 (rounds up because .9 ≥ .5). FLOOR(12.9) = 12 (always goes down regardless).
  • Common use: Age calculation (how many COMPLETE years), quota calculations (how many complete units fit), truncating timestamps to day/hour boundaries.

ABS() — Absolute Value

  • ABS = Absolute value. Returns the magnitude of a number regardless of its sign. Always returns a non-negative result.
  • ABS(-25) → 25. ABS(25) → 25. ABS(-3.14) → 3.14. ABS(0) → 0.
  • Mathematical meaning: The distance from zero on the number line, without direction. |-25| = |25| = 25.
  • Common use: Finding the difference between two values regardless of order — ABS(price_a - price_b) gives the gap without caring which is larger. Detecting anomalies (variance from expected). Calculating error margins.

MOD() — Remainder (Modulo)

  • MOD = Modulo / Modulus. Returns the remainder after dividing the first number by the second.
  • Syntax: MOD(dividend, divisor)
  • MOD(25, 7) → 25 ÷ 7 = 3 remainder 4 (3×7=21, 25-21=4) → returns 4
  • MOD(10, 2) → 10 ÷ 2 = 5 remainder 0 → returns 0 (even number check!)
  • MOD(10, 3) → 10 ÷ 3 = 3 remainder 1 → returns 1
  • In many databases you can also use the % operator: 25 % 7 = 4.
  • Common uses:
    • Even/odd check: MOD(id, 2) = 0 → even rows only
    • Cyclic assignment: MOD(row_number, 3) distributes rows into 3 groups (0, 1, 2)
    • Pagination: which page does row N belong to?
    • Time calculations: MOD(minutes, 60) = remaining minutes after full hours

🔵 INTERSECT — Common rows between two queries

Returns only the rows that appear in BOTH query results. Removes duplicates automatically.

Definition — word by word

  • INTERSECT — From set theory: the intersection of two sets = elements that belong to BOTH sets. Example: Set A = {1,2,3,4}, Set B = {3,4,5,6} → Intersection = {3,4}.
  • Returns common rows — Only rows that exist in BOTH the first SELECT and the second SELECT are returned. If a row exists in only one query, it is excluded.
  • Removes duplicates — Like UNION (not UNION ALL), INTERSECT automatically deduplicates the output. Each unique common row appears exactly once.
  • Column names and data types must match — The number of columns in both SELECTs must be identical, and each column pair must have compatible data types (e.g., both VARCHAR, both INT). The column names in the output come from the FIRST SELECT.

Syntax (from image)

SELECT column_list FROM table1 INTERSECT SELECT column_list FROM table2;

Example

-- Find customers who placed orders AND made payments SELECT customer_id FROM orders INTERSECT SELECT customer_id FROM payments; -- Returns: only customer_ids that appear in BOTH tables

BigQuery workaround (no INTERSECT)

-- BigQuery doesn't support INTERSECT directly — use INNER JOIN instead: SELECT DISTINCT o.customer_id FROM orders o INNER JOIN payments p ON o.customer_id = p.customer_id;

🔴 EXCEPT / MINUS — Rows in first query NOT in second

Returns rows from the FIRST query that do NOT appear in the SECOND query. Rows only in the second query are ignored. Removes duplicates automatically.

Definition — word by word

  • EXCEPT — The standard SQL keyword (SQL standard, ISO/ANSI). Used in PostgreSQL, SQL Server, BigQuery. Means "take away" — subtract the second result set from the first.
  • MINUS — Oracle's proprietary keyword for the same operation. EXCEPT and MINUS do exactly the same thing — only the keyword differs depending on the database.
  • "Returns rows in first query not in second" — Like mathematical set subtraction: A - B. If a row exists in query A but NOT in query B → it appears in the output. If a row exists in both A and B → it is excluded. If a row exists only in B → it is completely ignored.
  • "Removes duplicates" — Like INTERSECT and UNION (without ALL), EXCEPT automatically deduplicates the output. Each unique qualifying row appears exactly once.
  • Column names and data types must match — Same rule as all set operators: same number of columns, compatible data types, column names taken from the first query.

Database Support

  • PostgreSQL — Uses EXCEPT ✓
  • SQL Server — Uses EXCEPT ✓
  • BigQuery — Uses EXCEPT ✓ (BigQuery supports EXCEPT but NOT INTERSECT)
  • Oracle — Uses MINUS (Oracle does not support the word EXCEPT)
  • MySQL — Uses EXCEPT from version 8.0.31+ (older MySQL: use LEFT JOIN workaround)

INTERSECT vs EXCEPT — The Key Difference

INTERSECT → "What do BOTH have in common?" → rows in A AND B
EXCEPT/MINUS → "What does A have that B doesn't?" → rows in A but NOT in B

Think of it like: INTERSECT = overlap zone of a Venn diagram. EXCEPT = the left-only zone of a Venn diagram.

Syntax

-- Standard SQL (PostgreSQL, SQL Server, BigQuery): SELECT column_list FROM table1 EXCEPT SELECT column_list FROM table2; -- Oracle: SELECT column_list FROM table1 MINUS SELECT column_list FROM table2;

Real-world Examples

-- Example 1: Find customers who registered but NEVER placed an order SELECT customer_id FROM customers EXCEPT SELECT customer_id FROM orders; -- Returns: customer_ids in 'customers' that are NOT in 'orders' -- Example 2: Find products in catalog but NEVER sold SELECT product_id FROM products EXCEPT SELECT product_id FROM order_items; -- Example 3: Find employees who have NOT attended training SELECT emp_id FROM employees EXCEPT SELECT emp_id FROM training_attendance; -- Oracle equivalent of Example 1: SELECT customer_id FROM customers MINUS SELECT customer_id FROM orders;

EXCEPT vs LEFT JOIN — Two ways to find "missing" rows

-- Using EXCEPT (cleaner, declarative): SELECT customer_id FROM customers EXCEPT SELECT customer_id FROM orders; -- Using LEFT JOIN (more universal, works in older MySQL): SELECT c.customer_id FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id WHERE o.customer_id IS NULL; -- Both return the same result: customers with no orders

Important: Order matters for EXCEPT/MINUS

A EXCEPT B ≠ B EXCEPT A

A EXCEPT B = rows in A not in B
B EXCEPT A = rows in B not in A

Unlike UNION and INTERSECT (which are commutative — order doesn't matter), EXCEPT is NOT commutative. The first query determines which set you are "subtracting from."

📖 All 4 Set Operators — Explained

UNION — Combine + Remove Duplicates

  • Combines rows from two queries into one result set and removes all duplicate rows.
  • Like a mathematical set union: A ∪ B = all elements in A or B, without repetition.
  • Requires sorting/hashing to find and remove duplicates → slower than UNION ALL.
  • When to use: When you want all unique values from two sources — e.g., all unique customers who either placed an order OR made an enquiry.
SELECT name FROM customers_2023 UNION SELECT name FROM customers_2024; -- Returns all unique names from both years (no duplicates)

UNION ALL — Combine + Keep ALL Duplicates

  • Combines rows from two queries into one result set and keeps ALL rows including duplicates.
  • No deduplication step → faster than UNION. Use this by default unless you specifically need deduplication.
  • The total row count = count(query1) + count(query2) always.
  • When to use: Combining data from partitioned tables (monthly sales tables combined into one result). When you know there are no duplicates. When you want to count all occurrences including repeats.
SELECT product_id, revenue FROM sales_q1 UNION ALL SELECT product_id, revenue FROM sales_q2; -- Returns all rows from both quarters, duplicates included

INTERSECT — Only Common Rows

  • Returns rows that exist in BOTH queries. If a row is only in one query, it is excluded. Automatically deduplicates.
  • Like the overlapping region of a Venn diagram.
  • Not supported in BigQuery (use INNER JOIN instead). Supported in: SQL Server, PostgreSQL, Oracle.

EXCEPT / MINUS — Rows in First Query NOT in Second

  • Returns rows from the first query that do NOT appear in the second query. Rows that exist only in the second query are ignored.
  • Like subtracting one set from another: A - B = elements in A that are not in B.
  • EXCEPT — The standard SQL name. Used in PostgreSQL, SQL Server.
  • MINUS — Oracle's equivalent of EXCEPT. Same behaviour, different keyword. In BigQuery, use EXCEPT.
  • Automatically removes duplicates from the result.
  • When to use: Find customers who registered but never placed an order. Find products in catalogue but never sold. Identify missing/orphaned records.
-- Find customers who registered but never placed an order SELECT customer_id FROM customers EXCEPT SELECT customer_id FROM orders; -- Returns customer_ids that are in customers but NOT in orders

📖 Every JOIN — Word by Word

INNER JOIN — Only Matching Rows

  • INNER = inside the overlap. JOIN = combine tables. INNER JOIN returns only the rows where the join condition is TRUE in BOTH tables. If a row in the left table has no match in the right table (or vice versa), it is excluded entirely.
  • "Only matching rows" — The intersection of the two tables based on the join key.
  • This is the default JOIN type — writing just JOIN without a keyword means INNER JOIN.
SELECT e.name, d.dept_name FROM employees e INNER JOIN departments d ON e.dept_id = d.dept_id; -- Only employees WHO HAVE a matching department are returned -- Employees with dept_id = NULL are excluded -- Departments with no employees are excluded

LEFT JOIN — All Left + Matching Right

  • LEFT = the first (left) table. JOIN = combine. LEFT JOIN returns ALL rows from the LEFT table, plus the matching rows from the right table. Where there is no match in the right table, the right table columns are filled with NULL.
  • "All left + matching right" — The left table is fully preserved. The right table may contribute NULLs where no match exists.
  • Also called LEFT OUTER JOIN (the OUTER is optional).
  • Common use: Find all records from the main table with optional related data. Find orphaned records (WHERE right.id IS NULL).
SELECT e.name, d.dept_name FROM employees e LEFT JOIN departments d ON e.dept_id = d.dept_id; -- ALL employees returned -- If an employee has no department → dept_name = NULL -- Departments with no employees NOT shown -- Find employees WITHOUT a department: SELECT e.name FROM employees e LEFT JOIN departments d ON e.dept_id = d.dept_id WHERE d.dept_id IS NULL;

RIGHT JOIN — All Right + Matching Left

  • RIGHT = the second (right) table. RIGHT JOIN returns ALL rows from the RIGHT table, plus matching rows from the left table. Where there is no match in the left table, left columns are NULL.
  • "All right + matching left" — The right table is fully preserved. The left table may contribute NULLs.
  • Also called RIGHT OUTER JOIN. Less commonly used — most queries can be rewritten as a LEFT JOIN by swapping the table order.
  • Common use: When you receive a query written with the "main" table on the right side, or to find departments that have no employees.
SELECT e.name, d.dept_name FROM employees e RIGHT JOIN departments d ON e.dept_id = d.dept_id; -- ALL departments returned -- If a department has no employees → e.name = NULL -- Useful to find departments with no staff: WHERE e.emp_id IS NULL

FULL OUTER JOIN — All Rows from Both

  • FULL = complete. OUTER = includes unmatched rows from both sides. JOIN = combine. FULL OUTER JOIN returns ALL rows from BOTH tables. Where there is a match, columns from both tables are populated. Where there is no match (from either side), NULLs fill in the missing side.
  • "All rows from both" — The union of LEFT JOIN and RIGHT JOIN combined. No row from either table is ever excluded.
  • Also called FULL JOIN (OUTER is optional).
  • Not supported in MySQL (use UNION of LEFT JOIN + RIGHT JOIN as a workaround). Supported in: PostgreSQL, SQL Server, Oracle, BigQuery.
  • Common use: Reconciliation between two datasets — find records in A but not B, in B but not A, and in both. Data quality comparisons. Merging two reference tables that may have different coverage.
SELECT e.name, d.dept_name FROM employees e FULL OUTER JOIN departments d ON e.dept_id = d.dept_id; -- Employees WITHOUT a department: shown with NULL dept_name -- Departments WITHOUT employees: shown with NULL e.name -- Matching pairs: shown with both sides populated

CROSS JOIN — Cartesian Product

  • CROSS = crossing all combinations. JOIN = combine. CROSS JOIN returns every possible combination of rows from the left table with rows from the right table. No join condition is used.
  • "Cartesian product" — From mathematics: the Cartesian product of sets A × B = all ordered pairs (a, b) where a ∈ A and b ∈ B. If table A has 100 rows and table B has 50 rows → CROSS JOIN returns 100 × 50 = 5,000 rows.
  • Warning: CROSS JOIN on large tables creates enormous result sets. 1,000 × 1,000 = 1,000,000 rows. Always be careful.
  • No ON clause is used (or needed) — there is no join condition.
  • Common use: Generate all possible combinations — all products × all stores, all sizes × all colours, all dates × all regions. Used in report frameworks to ensure every combination appears even if no data exists.
SELECT s.size, c.color FROM sizes s CROSS JOIN colors c; -- If sizes has 3 rows (S, M, L) and colors has 4 rows (Red, Blue, Green, Black) -- Result: 3 × 4 = 12 rows: (S,Red), (S,Blue), (S,Green), (S,Black), (M,Red)...

SELF JOIN — Join Table with Itself

  • SELF = itself. A SELF JOIN is when a table is joined to itself. This is done by giving the table two different aliases to treat it as two separate tables.
  • "Join table with itself" — The same table appears on both the left and right sides of the join, but with different aliases so SQL can distinguish between the two "copies."
  • Not a separate SQL keyword — it is an INNER JOIN, LEFT JOIN, etc., but both sides reference the same table.
  • Common use cases:
    • Employee-Manager hierarchy — employees table has a manager_id column that references another employee_id in the same table. Self join to find each employee's manager's name.
    • Hierarchical/recursive structures — org charts, category trees, comment threads.
    • Find duplicates — join a table to itself on matching column values but different IDs.
-- Find each employee and their manager's name SELECT e.name AS employee, m.name AS manager FROM employees e INNER JOIN employees m ON e.manager_id = m.emp_id; -- 'e' is the employee side, 'm' is the manager side -- Both point to the SAME employees table
